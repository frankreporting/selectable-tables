# Selectable Tables

An Obsidian plugin (`selectable-tables`) that makes a Live Preview table one block for the arrow keys: ↑/↓ pass it in one press, and ←/→ at its edge select it whole, like an image. Enter then selects a cell, and the arrows move between cells without opening them. `AGENTS.md` holds the generic Obsidian plugin rules (manifest, releases, API use); this file holds what's specific to this repo and overrides it.

## What the plugin relies on in Obsidian

These are Obsidian behaviors, not calls, so any Obsidian update can change them. `scripts/obsidian-check.js` tests them first; run it after each Obsidian update (its header says how).

1. A rendered table is one block widget in the editor, carrying the class `cm-table-widget`.
2. A caret inside a table's text opens a cell; a selection over the whole table opens none.
3. Focusing the note's editor closes an open cell.
4. A table's rows and cells on screen line up with its text: the header is row 0, the delimiter line has no row, and a short row is filled with empty cells.
5. A caret in a cell's text opens exactly that cell.
6. The selected table's tint is drawn on the table element, so the plugin can take it off while a cell is selected.
7. A press on a cell of a malformed table tidies it, which is what makes Enter work on it again. A table with only unusual padding stays as it is, and a press still opens its cells.
8. Opening a cell hides its rendered text's `.table-cell-wrapper` with an inline `display: none`, and builds a new `.table-cell-wrapper` beside it, holding the editor's own element, which holds `.cm-editor`. Closing the cell removes that box. `width-copy.ts` puts a copy of the rendered text right after the editor's element, and the copy holds the column's width. If this changes, no copy is made, and columns move again as in stock Obsidian.
9. Word jumps, Option+↑/↓, and the other moves a key can make across lines send the user event `select`. A click sends `select.pointer`, and Obsidian's own moves between cells send none.
10. Page Up/Down pass a drawn table from a line of text, since CodeMirror's page move steps out of block widgets. A table only becomes a block once Obsidian's parser reaches it, and a held key outruns the parser, so a table can still be lines of text when a move lands on it.
11. Obsidian binds Page Up/Down, Cmd+↑/↓, Ctrl+↑/↓ and Cmd+Home/End in a cell's editor as plain keys that hand over to the note, at a lower precedence than the plugin's keymap.
12. Vim puts `cm-vimMode` on the editor's scroller outside insert mode.
13. A table's widget is padded by `--table-drag-handle-size`, 16 px on a desktop and 24 px on a phone or tablet, and scrolls sideways itself, so it's the box `position: sticky` binds to, and frozen rows can't stick to the note's scroll. This holds for Obsidian's table; on a computer the plugin's own table has no box that scrolls (item 12 of *The plugin's own table*).
14. Building a table anew empties its widget and keeps the widget, and a table that leaves CodeMirror's drawn range comes back as the same widget.
15. A table in Reading view sits in an `.el-table` box with its own scroll, so frozen rows can't stick there either.
16. Opening a cell focuses its own editor, inside the cell, so the note's content hears `focusin`. Obsidian's scroll to the cell runs right after that, in the same task.
17. On a phone with Floating navigation or Auto full screen on, both the default, a note in the main pane runs to the top of the screen, under the status bar and a fixed header. `--view-header-top-offset`, `--view-header-height` and `--safe-area-inset-top` say where those end, and `is-hidden-nav` on the body says the header has hidden. A tablet's note starts below its header.
18. On a phone or tablet, `body.is-mobile .app-container` takes `--keyboard-height` off its height, so the keyboard shrinks the note's pane, in steps: the toolbar above the keyboard first, then the keyboard.
19. Obsidian sends `css-change` once a change of look is in place: after switching light and dark, which toggles the body's classes first, and after loading a theme or a snippet, or changing fonts. The Style Settings plugin sends it after changing a setting, its body classes included.
20. An editor command gets the note's editor even while one of its cells is open: the cell's editor keeps the note's view as the active editor, and carries the note's `editorInfoField`, so `noteView` in `extension.ts` leaves cell editors out.
21. A right-click on a cell that isn't open shows Obsidian's menu for the table, made with `Menu.forEvent`, which prevents the event's default and gives the same menu to a later listener on that event: `tableMenus`, on the note's content, adds the freeze items there. A right-click in an open cell fires `editor-menu` with the cell's own editor, and the note's view as its info, whose editor is the note's. A right press on a cell doesn't open it. On a Mac, menus are native unless the vault says otherwise, and Obsidian builds those from the same items, so the check script has Obsidian draw them for its run.
22. A comment in a cell draws nothing, and the space typed beside it stays in the cell's text: Obsidian draws a cell by rendering `| <its text> | | - |` and taking the header cell's contents, and its cells keep every space (`--table-white-space: break-spaces`, in the default theme). Opening, editing or closing a cell empties and refills what's inside it and keeps the cell's element, so a class on a `th` stays until the table is built anew.

A release build makes no private Obsidian calls; a preview build makes the language copy of *The plugin's own table*, and the borrowed cell editor's five (*Editing a cell*, there). A release reads only CodeMirror's public layout (`lineBlockAt`, `posAtDOM`, `moveVertically`), `editorLivePreviewField`, `editorEditorField` and `editorInfoField`, plus eight classes Obsidian puts in the DOM: `cm-table-widget`, to tell a cell's editor from a note's, `table-cell-wrapper`, to find an open cell's rendered text and its editor's box, and the open cell a command acts on, `mod-image-selected`, `has-selection`, which marks a dragged range of cells and keeps its right-click menu Obsidian's own, `table-row-drag-handle` and `table-col-drag-handle`, whose menus stay Obsidian's own too, `cm-vimMode`, and `is-mobile`, so frozen rows restart only on a phone or tablet. The right-click menu uses only the public `Menu.forEvent` and `editor-menu` (item 21). `styles.css` also reads item 17's classes and variables.

**How a table freezes.** The mark, `%%freeze 2 1%%` in any header cell, is the only record, so `freeze.ts` reads it when a table is drawn and when a change touches its header line, and nothing runs as the note scrolls. The commands write it before the first header cell's text, or over the mark already there, in one transaction. It carries `writesTable`, which the edit guard lets through on a selected cell, and `isolateHistory`, so the history never joins it with another edit and Undo takes it back alone. `@codemirror/commands` is a dev dependency for that one's type only, pinned to a version that takes the same `@codemirror/state` as `obsidian`: Obsidian gives plugins its own copy at run time. A header the mark can't go in safely, where a cell would lose text or the mark wouldn't read back, gets a notice and no change. The mark widens its column, and Enter opens a cell only in a table padded as Obsidian pads it, so a table Obsidian wrote is padded again that way (`rewrittenWith` in `table-text.ts`); any other table keeps its spacing, and only its header line changes. An open cell is closed and selected first, as Escape does it: Obsidian routes a change inside an open cell through the cell's own editor. Frozen columns are `position: sticky`, picked by `:nth-child`, because a class on every cell of a long table costs too much. Frozen rows can't stick (item 13), so a CSS scroll-driven animation on each row moves it with the note. It runs on the compositor, where the scroll does, so rows don't trail a real gesture, which a script's do. A script setting `scrollTop` runs on the main thread and hides that, so a timing check needs real input (`Input.synthesizeScrollGesture`), and only `capturePage` shows where rows are really drawn: page state reads correct when they aren't.

**A mark's space.** The commands write the mark with a space after it, `%%freeze 2 1%% Name`, and people type it that way. The mark draws nothing, but the space stays at the start of the cell (item 22), and in a column only as wide as "Name" it takes a line of its own, making the header row a line taller. So `freeze.ts` puts `selectable-tables-mark-cell` on every header cell holding a mark, frozen or not, each time it reads a table's header line, and `styles.css` gives that cell `white-space-collapse: collapse`: it drops spaces at a line's start and end and shows two in a row as one, as the 20 themes that set `--table-white-space: normal` do for every cell. Only the longhand, so wrapping stays as the theme set it: Minimal's and Baseline's no-wrap table settings still hold. An open cell's editor sets its own spacing, so the source shows as typed. Don't take the space out of the text instead: Obsidian's editor reads `#` as a tag only after a space, so a mark written right against `#tag` would stop it being a tag there, and marks already typed would keep the line. Reading view, where the plugin doesn't run, still keeps the space; STA-38 holds that.

Three things about frozen tables aren't obvious. When a theme collapses a table's borders, as the default theme does, a frozen table switches to separate ones, because collapsed borders stay behind when cells move, and its cells draw their own with Obsidian's variables. A theme with separate borders, Baseline say, already has each cell draw its own lines, so they're left alone. Sizes go on the rows, not the table, since a variable on the table restyles every cell; the one exception is a second or later frozen column's offset, which has to sit above all its cells, and changes only when a frozen column's width does. And the rows' animation runs 4000 px past the pane's top, with its easing holding them at the table's end. Without that it finishes as the table leaves the pane, and a finished animation isn't kept on the compositor, so a hard flick back into the table would draw the rows too low until the page caught up.

**A theme's colors.** Frozen cells have to be solid, since cells pass under them, so each is painted with what shows behind it unfrozen: the cell's own color, its row's, its header's or body's, the table's and the widget's, over the first solid color behind the table. `theme-paint.ts` reads these from computed styles, for the header's odd and even cells and the body's odd and even rows', since odd and even are what themes stripe by, and lays them as one-color gradients, so the browser blends them as it blends the elements and no color is parsed. Only opacity is read, to know where to stop. The read has to come before marking, since `styles.css` paints over the theme's colors, and reading a table that's just been drawn makes the browser work out its styles, which marking then has it do again: 2.4 ms on 50 rows, 81 on 2,000. So each editor keeps what it read by place, the classes of everything around the table less those that only mark focus and the like, and reads only the first table in each. A table too small to show every kind of row and cell, with a last row or cell among those read, or with a row under the pointer, is read but not kept. On `css-change` each editor forgets them all and, on its next frame, reads every frozen table on screen again: a popout window takes on the new look a moment after the event, and the font size slider sends one on every step. A color in the middle of a transition is read where it ends. A widget can outlive the plugin out of the drawn range, so one that still carries a freeze's marks when a new copy first sees it is cleaned from what's on it, before anything reads it. A theme's own picture behind cells, such as a texture, isn't kept, and nor are hover colors; STA-47 looks at what other themes still need.

**A cell's corners.** A frozen cell is solid only inside its shape, so where a theme rounds its cells, as Baseline does, rows passing under a pinned row would show at its cells' corners. The browser draws a cell's color, and its row's and its header's or body's, inside the cell's rounding, so at rest the corners show the table's color, over what's behind the table. `theme-paint.ts` reads that, starting at the table instead of a cell, into `--selectable-tables-corners`, and each pinned row lays it under its cells as an inset shadow. Only the row's shadow can do this: a color on the row is drawn inside each cell's rounding too, a pseudo-element on a row changes the table's layout, and one on a cell covers only that cell, since Obsidian positions the cells. Where nothing is rounded, the cells cover the shadow. What it leaves, all in STA-66: WebKit draws no shadow on a table row, so on iPhone and iPad the corners still show what passes, and a frozen header cell's corners still show the header cells that pass under it sideways, since those are in the same row, above its shadow. And the shadow makes the row solid, which hides anything the browser draws for the table outside the row: a theme that colors its header and rounds its cells gets corners a hair thinner at rest, and Sanctum's *Sticky headers*, which makes the header a table of its own with collapsed borders, loses the line under it at rest as well as pinned (STA-64).

Anything that has to keep up with a scroll must run where the scroll does: `transform`, `opacity` or `position: sticky`. An animated `clip-path` runs on the main thread, so a table scrolling sideways outruns it, and the clip snaps back on each frame. That's why the selected table's tint is kept out of the strip beside a frozen column by a sticky cover, not a clip. And a pinned row can't scroll to give its cell room, so a positive `scroll-margin` on it moves the note on every key: a cell there has a margin of -1px. For the same reason `scrollIntoView` does nothing on a frozen cell, so a key that moves up or left into one calls `backToStart` in `freeze.ts`, or the rows and columns beside it would stay hidden. `decide.ts` says which keys those are: moving along a pinned row must not scroll.

`backToStart`, `show` in `cells.ts` and frozen columns all assume a table's start can be scrolled to. A theme that centers a table in its box with flex breaks that once the table is wider than the box: it sticks out on both sides, and the side at the start is out of reach. Baseline does this with Table width on Auto (Center), and so does One Oracle Developer, built on it. So `styles.css` gives every table's box in a note the plugin runs in `justify-content: safe center`, which centers a table that fits and starts a wider one at the box's edge, and does nothing on a box that isn't flex or grid. It names no theme, and its five classes beat Baseline's four in either load order. A theme that centers with auto margins on the table instead, as Minimal does, already falls back to the start and needs nothing. MoreMonoColor sets the box's centering `!important`, so the rule can't win there, but its box shrinks to the pane and a wide table overflows only at its end. A theme that made the box flex to put tables at its start or end would get them centered; of 702 themes scanned on 11/4, none does. `.dev/themes/center.cjs` checks this headless.

**On phones and tablets.** A device without scroll-driven animations can't pin rows, so `freeze.ts` reads every table there as freezing nothing (`canFreeze`), and only marks the cells holding a mark, and its tables scroll as usual: an iPhone or iPad before iOS 26, and an old Android WebView. iOS 26.0 to 26.3 pass that check but run these animations on the main thread, so rows may trail the finger there, and CSS can't tell those versions apart. On a phone, `--selectable-tables-pin-top` in `styles.css` is where rows pin, from item 17: below the header, or the status bar once the header hides. It moves both ends of the rows' animation range, so the range's length, and `freeze.ts`'s sums, don't depend on it. The rows can't glide with the header, because a transition can't drive an `animation-*` property, in WebKit or Chromium. `app.emulateMobile` and the classes `scripts/obsidian-check.js` puts on the body show the layout, but scrolling and touch on a real phone are the only real test. WebKit runs headless through Playwright, with Obsidian's real `app.css`, for anything that doesn't need Obsidian itself.

**The keyboard on an iPhone, and frozen rows.** When the keyboard opens with the caret in one of a frozen table's cells, iOS's own copy of the rows' animation can stop following the scroll. It then draws the rows where they sit in the table, so they vanish from where they pin, while the page still has them pinned. A screen recording with Web Inspector's compositing borders on showed this on 11/2, so it's a WebKit fault; STA-43 holds the report for Apple. A caret in any cell triggers it, frozen row or not, and a caret on a text line hasn't. `restartRows` in `freeze.ts` clears it: on a phone or tablet, every change of the pane's height (item 18) starts the rows' animation again on a new timeline, in the resize observer's callback, before the pane is drawn at its new size. `selectable-tables-restarting` takes the timeline and the animation off for a moment, and the timeline comes back first. Reading a style in between brings both up to date without a layout, so a restart costs 0 to 1 ms on an iPhone, where a forced layout cost 6 to 19. Tried and dropped: restarting the animation alone made the rows blink, waiting 120 ms after the change let the fault show for about 0.13 s, and restarting only with the caret in a frozen row let it back in from a body cell. A known limit remains: the rows can flicker for a moment as the keyboard opens or closes, and the caret can drift inside its cell until the next key. The drift is probably the same kind of fault, since an open cell's editor gets a layer of its own inside the row. Tried on 11/1: moving the rows by `top` jitters constantly, sticky cells show gaps and take away the table's sideways scroll, and dropping `will-change` made no difference, so the rows keep it. A change here needs a control on the same build, since the fault is random enough that one run went 28,062 px between sightings. To load a new build on the phone: plugin off, force close Obsidian, reopen, plugin on.

**A cell stays clear of what's pinned.** Frozen rows and columns cover the cells that pass under them, and no scroll knows: the browser's and Obsidian's compare raw positions, and a cell's editor stops at a sticky cell, so typing in a frozen column's cell doesn't move the note at all. So `show` in `cells.ts` gives the cell scroll margins that reach past what's pinned, scrolls, and takes them off again, all in one go. It runs when a cell is selected, on the next frame after a frozen table's cell opens, and after a cell's editor scrolls to its caret, which an edit from Sync doesn't do. It also runs once a freeze command, Undo or Redo changes a header line with a cell selected (`showsCellAfter` in `decide.ts`), since Unfreeze sends a pinned cell back to its place in the table, which can be above the pane or off to its left. That one waits for the resize observer's callback after the new freeze is marked: the measure comes there, and so does it come after Undo and Redo's own scroll, which runs after everything a CodeMirror measure writes. An unfrozen table has nothing left to watch, so `freeze.ts` watches the pane anew, which sends a size at once. Undo's scroll takes the whole table into view, its far end on a long one, so Undo still moves the note when the cell was in view, and the cell ends at the pane's top. Keeping the note still there would mean replacing that scroll, with a check on every scroll into view, which is every keystroke; STA-55 holds that. Nothing else reads a scroll margin, so these sizes never go on the table, where a change would restyle every cell. `freeze.ts` measures them and leaves them in `pinnedTables`, in `cells.ts`, because `freeze.ts` already imports that file.

**The check on key moves.** `landing` in `decide.ts`, run as a transaction filter, is the one place that stops a key opening a cell: a move that sends `select`, other than a click's `select.pointer` or a search's `select.search`, and leaves one caret in a table's text selects the table instead, or is dropped from that same table selected or from a selected cell. So there's no list of keys to keep, and other plugins' move commands are covered too. Obsidian's Home, End and Cmd+←/→ send no user event, so the check can't see them; they can't cross a line, and the plugin's own bindings take them, with or without Shift, on a selected table or cell, and when a head sits on a table's edge. A browser-driven selection change gets `select` by default, so it passes through the check too. A big jump (Page Up/Down, Cmd+↑/↓, Cmd+Home/End, Ctrl+↑/↓) can land on a table that's still text, and a cell opens once Obsidian draws it; stock Obsidian does this too, on a held Page Down, but there the key carries on, while here Page Down in a cell stays in the table. So for these keys alone the check reads the table from the text and goes past it. Other keys don't, since text near the caret that reads as a table really is text, as in a code block. The check stands aside for what must still open a cell: a click, Enter's caret (`opensCell`), and a plain arrow the plugin left to Obsidian, which enters a table with no line beyond it. It also stands aside while Vim is driving, since selecting a table in normal mode would start Visual mode. On the plugin's own table it reads the plugin's list of tables, whole, and a caret anything else leaves in a table's text is taken by the caret rule (*The keys on it*).

**A selected cell is a class, not a selection.** The note's selection stays on the whole table, and a move between cells dispatches no transaction, because each one walks the whole note in Live Preview and runs every plugin's listeners. On the plugin's own table the table draws the class itself, as its rows are drawn, and still no move dispatches. So the edit guard is all that stops an edit meant for "the selection" from hitting the whole table. How edits reach it, read from Obsidian 1.15.0 and run on 10/30:

- Obsidian's editor commands, such as Toggle comment (Cmd+/), Toggle checkbox (Cmd+L) and Insert horizontal rule, send no user event. The table's own menus and + buttons send none either, and by then Obsidian has already changed the drawn table, so they must never be dropped: a press in the note takes the cell off first.
- A reload from disk, which is how Sync arrives, carries `userEvent: "set"`.
- A second pane on the same note arrives as a remote edit with `filter: false`, so it skips transaction filters.
- The freeze commands' own write, and the table edits' (*Editing rows and columns*, below), carry `writesTable`, which passes.

**A caret doesn't repair a table; a press does.** Obsidian keeps its own model of a table's cells, and marks the table malformed when its text isn't what the table editor writes (uneven rows, other padding), or after closing a cell trims it, which changes the model without telling the note. A press opens a cell through `setCellFocus`, which rewrites a malformed table first. A caret landing in a cell skips that, and then typing can eat a pipe, or never reach the note. So Enter opens a cell only when `writtenByObsidian` in `table-text.ts` says the table's rows are exactly what Obsidian's editor would write. That check rebuilds the rows and compares them, on purpose: a wrong answer usually costs a click, while a check that tries to predict Obsidian's private flag can let a corrupting caret through. It can't see a stale model behind exact text, which undo can leave after a cell's trailing spaces are trimmed; a stock click does the same damage there. Don't bring back a keyboard repair by putting the caret on the delimiter line: it rewrites the table with the caret there, so undo goes back to that caret and Obsidian rewrites the table again, and undo can never get past it. Stock Obsidian has the corruption too when you arrow into a table.

**Never interfere with a running composition.** Dropping composed input in the guard, or moving the selection in `compositionstart`, leaves `view.composing` true for good. CodeMirror then ignores keys, and Live Preview stops rebuilding, so new notes draw no tables until the editor is replaced. An input method's first keydown comes before its composition, and that's the only safe moment to move the selection. Its `key` is the real letter on a Mac, `Process` on Windows and Linux, `Unidentified` on Android, and `Dead` for a dead key such as Option+E, so typing on a selected table or cell is told by `key`, with no `keyCode`. Left alone, a real input method on a selected table replaced the table with its first letter and put the rest below the next table (STA-46's probe, 11/2). With Japanese, Enter after Space leaves the text underlined, and a second Enter ends the composition, on a plain line too. Simulated composition (`Input.imeSetComposition`) must be finished with `Input.insertText`, or it freezes the test window the same way. Editor commands like Toggle line numbers are saved to the vault's tracked `app.json`, so a sweep of commands has to skip them.

A table is a block widget over text that reads as a Markdown table. At a note's start or right below the frontmatter, Obsidian draws a table with an exclusive start, and CodeMirror then reports the line as an empty text part plus the widget; `partAt` in `layout.ts` handles that. Obsidian keeps a blank line around the tables it makes, so a table with no line beside it only comes from a note written elsewhere, and isn't a case to plan or test for. `Table first`, `Table last` and `Properties then table` in the test vault are written that way by hand, so they don't show what real notes do. Unit tests use a fake layout (`test/notes.ts`), which can't show such details, so check layout changes against a real editor too. Since the check is the text, another plugin's block widget drawn over table Markdown would count as a table too.

## The plugin's own table (preview builds)

The plugin can draw Live Preview tables itself, so a large table stays fast: only the rows near the pane are in the page, and a table of more than 100 rows is a block per 100 rows (`blocks.ts`), so CodeMirror counts only the blocks near the pane as on screen, and the parser and Live Preview do only that much after each key. It's behind a switch, the command *Draw tables with the plugin (preview)*, until Obsidian's table controls are rebuilt on it (STA-76's later sub-issues). Only a preview build has it: `npm run build:preview`, `npm run dev` and `npm run test-vault` make one, and `npm run build` makes a release, in which `esbuild.config.mjs` puts `src/preview-off.ts` where `./preview` is imported and fails if the renderer's row class is in `main.js`. The renderer's CSS is `src/own-table/styles.css`, which `install-test-vault.mjs --preview` adds to `styles.css` in the vault; the release's `styles.css` doesn't have it. The switch is saved in the plugin's data. With it on, `freeze.ts` isn't loaded (the plugin's table pins frozen rows and columns itself, *Frozen rows and columns*, below), and the navigation layer runs on the plugin's table (*The keys on it*, below): `preview.ts` swaps the editor extensions in the array `main.ts` registers and calls `workspace.updateOptions()`. Obsidian's right-click Row, Column and Sort items and its table commands are rebuilt on it (*Editing rows and columns*, below), and so are its drag handles and + buttons (*Drag handles and + buttons*, below).

**What it relies on in Obsidian.** Read from 1.15.1 and checked by the *Own* section of `scripts/obsidian-check.js`, which runs only in a preview build, with the switch on; the sections before it run with the switch off.

1. Obsidian finds a Live Preview table only by the line class `HyperMD-table-row` in the syntax tree (its Live Preview builder; two other checks read `HyperMD-table` and `HyperMD-table-2`).
2. A note's editor gets its Markdown language in `buildLocalExtensions`: a `StreamLanguage` of the CodeMirror 5 mode `hypermd` (`parseFrontmatter ? Ake : Pke`), and nothing compares it by identity. So a copy made with `StreamLanguage.define` from its `streamParser` (internal to CodeMirror), whose token function gives a table row's first token only `line-selectable-tables-row` and its other tokens nothing (`hide-rows.ts`), hides every table from Obsidian: it builds no table object, and its parser no longer reads every table to its end, since rows lose `line-parse-next`. HyperMD keeps the table it's in on its state as `hmdTable`. This is the private change.
3. Obsidian's parser gives every line with a class one node over the line, and its own `@codemirror/language` exports the prop holding the classes as `lineClassNodeProp`; CodeMirror's doesn't, so it's read by name (`tree-rows.ts`).
4. The copy goes in as the editor is made: a `language.computeN` at `Prec.highest` gives it in Live Preview and nothing in Source mode, from a field that holds the copy for the editor (`language.ts`). Obsidian creates a note's state with `editorEditorField` and `editorInfoField` set, and the plugin's extensions in it, so the field can tell a note's editor (its info is a `MarkdownView`, and it isn't inside a `.cm-table-widget`) and give it the copy of the language the last note's editor had. The first note after Obsidian starts, or after the switch goes on, gets it a moment later, from a view plugin, after one first parse on Obsidian's language. Obsidian's own cell editors and editors outside a note (a canvas card) keep Obsidian's language and its tables. Before using a copy, the plugin parses a small table with it and checks the rows it marks; if the copy can't be made, after an Obsidian update say, it leaves tables to Obsidian and says so once.
5. Tables start where the parser marks a header row; each one's end is read from the text, by the parser's own rule (`rowRule` in `find.ts`: a header starting with a pipe goes on while lines start with one, any other while a line has a pipe after a first character that isn't one). The parser reads only so far past the screen, and when it's 100,000 characters behind the screen it starts again near it, leaving the stretch between with nothing on it: a table there keeps its place while its text still opens a table. After a change, `updateTables` reads only from the line above the first change to where the parser has read, and skips over tables it still marks.
6. `MarkdownRenderer.render` draws a table's rows as Reading view does, and the editor's own link handling (`registerDomEvents` on its content, with `Dv`) follows a link in a rendered cell and shows its preview on hover, as in Obsidian's table. It doesn't mark a link to a missing note, so the renderer does (`getFirstLinkpathDest`). Its table post-processor sets each cell's `dir` from its first strong character before `render` returns, reading it with a node iterator rooted at the cell (`G6`); Obsidian's own table also puts the first cell's on its box, so a table whose first cell reads right to left runs from the right. The renderer puts the first header cell's on each block and on the box around them, and each cell's on the cell's own box (`.table-cell-wrapper`): cells that draw their own borders do it by direction, and a cell reading the other way would leave the table's end bare. A document keeps every node iterator until a garbage collection and checks each one whenever a node in it moves, and an iterator follows its root into another document. So `renderBatch` renders each batch in a document of its own and moves only the cells' contents into cells it makes in the page, with the rendered cells' attributes. Rendered in the page, a fast scroll piled up thousands of iterators there, and every change in the page, Obsidian's too, got slower until the next collection.
7. A table of up to 100 rows is one block widget carrying Obsidian's classes for its table (`cm-embed-block cm-table-widget markdown-rendered`), so Obsidian's look and a theme's land on it; a longer one is a block per 100 rows, each such a widget (item 9). A block's `coordsAt` says where each row is, or CodeMirror scrolls to the block's end for a line in it. Columns get fixed widths worked out from the text with the theme's fonts and sizes (`estimate.ts`, read by `metrics.ts` from a hidden table), so they hold as rows come and go. Rows are drawn to 1,500 px past the pane, measured, and the row at the pane's top kept still while rows above take their real heights. Spacer rows stand in for the rest, hidden from screen readers, and a hidden row keeps the drawn ones odd or even; each drawn row carries `aria-rowindex` and the table `aria-rowcount`, so a screen reader hears where a row sits in the whole table. Where the theme collapses borders, the box takes `selectable-tables-own-borders`, as a frozen table does, and its cells draw their own: collapsed borders belong to the whole table, so each row added repainted all of it on screen, and hard flicks blanked the pane about twice as often. The first column gets half of each of its borders back, so its text has the room it has in Obsidian's table.
8. A press on a cell opens it (*Editing a cell*, below), and a press beside the cells, or on the box around a table's blocks, selects the table whole, with Obsidian's tint and the frame `styles.css` draws for a selected table. Typing over it does nothing (`stopsEdit`, as for the navigation layer); Delete, cut and paste act on it.
9. CodeMirror puts a box around a run of lines, a block wrapper (`@codemirror/view` 6.39; Obsidian 1.15.1 bundles 6.43 or later). Each table of more than 100 rows gets one around its blocks (`boxes.ts`), with Obsidian's classes for a table's box, so Obsidian's and a theme's sizes for that box (its reach into the margins, its padding beside the table, a theme's width) land on it once. The blocks inside drop them, `!important` for their margins, since Obsidian and themes set a table box's margins that way; and the box drops its padding above and below, which CodeMirror can't see, so the first block keeps the padding above and the last the padding below. Themes style a table's first and last rows, so each block has hidden first and last rows that only count for those rules, and a hidden row keeps every drawn row odd or even as in the whole table. On a phone or tablet the box scrolls the blocks sideways together; on a computer it clips them (item 12). CodeMirror makes the box anew whenever the first block it draws changes, and the new box starts at the table's left edge, so a mutation observer on the content puts it back where the table was, before the frame is drawn; only a box just put in the page, so the box already there keeps a swipe's place. Block wrappers are read by name, since npm won't install a newer `@codemirror/view` beside the `obsidian` package's pin; without them the plugin leaves tables to Obsidian and says so once.
10. CodeMirror keeps the note still on its scroll anchor: the line block at the scroll offset plus 8 px, from its own heights, at the start of a measure (`scrollAnchorAt`), and moves the note for any change of height above that block. So the plugin keeps the row at the pane's top still only for rows above it in that same block, and a block coming into view starts at its full estimated height, its rows not drawn yet standing in as spacers; otherwise both would move the note for the same rows. CodeMirror keeps a block's height until it draws it again, and takes an estimated height only from a new decoration, so tables shaped since they were decorated (before they had sizes, or after the pane or the theme changed) are decorated again.
11. With blocks, the screen can start inside a table, so after the parser's 100,000-character jump (item 5) it can start again on one of a table's rows and read the rest as text, its header in the stretch it skipped. An edit above the table with the note scrolled to its end does this, for about 12 frames before the parser reads the header again. A table the plugin already knows is kept while its header is in a stretch the parser skipped and its text still opens a table (`updateTables`), so it's never drawn as lines of text.
12. **Sideways, on a computer (STA-79).** A box that scrolls a table sideways stops its rows sticking to the note (item 13 of the list above), so on a computer no box does: the table's box, its one block or the box around its blocks, clips it (`overflow: clip`, which makes no scroll container), and each block's `.table-wrapper` moves by a transform that follows a scrollbar of the plugin's own (`bar.ts`), a scroll-driven animation on the compositor, so the blocks move as one with no script as they move. The bar is a scroller in the note's `.cm-scroller`, as wide as the table's box, whose content is that much wider than the table can move: its scroll is the table's place sideways, kept while the table is wide, so it survives the table leaving the pane and CodeMirror rebuilding its box. Its `scroll-timeline` is named per table and hoisted by `timeline-scope` on the scroller, so every block in it can follow it. It sits in the scroller, not beside it, so scrolling up and down with the pointer over it scrolls the note, and it has no styling of the plugin's, so on a Mac it's the system's own bar and follows Show scroll bars, and elsewhere Obsidian's `styled-scrollbars` styles it. Its place up and down is an animation on the note's own scroll: it sits under the table's last row, in the box's bottom padding, and between two scroll offsets worked out from where the header and the last row sit in the note's content, it rides the pane's bottom, clear of the status bar (`.status-bar`, read where it floats over the pane), so it never trails a scroll; the sums are `barPlace` in `sideways.ts`. A table no wider than its box gets no bar and no transform. The scroll range is rounded to whole pixels, as Obsidian's box rounds its own, which also keeps the table's lines sharp. A swipe over the table sends no scroll the browser can use, so a wheel listener on the content, not passive, passes the sideways part of a mostly sideways swipe to the bar and stops the note scrolling for it, and leaves a swipe that starts up or down alone (`Swipes`): as in Obsidian's box, where the browser keeps a swipe to where it began. Obsidian already listens for the wheel that way on the note's view, for Ctrl-zoom, so a swipe's first event waited on the page before. A swipe starts anew after a pause of 80 ms, or when the browser starts one, which it marks by letting its first event be cancelled. Ctrl with the wheel, and a pinch, are Obsidian's. Phones and tablets keep the box, scrolled by a finger, which sends no wheel events, and so do browsers without scroll-driven animations: `usesBars` reads `is-mobile` on the body and `CSS.supports`, and the editor carries `selectable-tables-bars` when it uses bars. `showSideways` on a model brings part of a table into view sideways, in the bar or the box, for the table keys, the open cell and frozen columns to use. A block that comes into the page carries the bar's timeline from its first frame, so it's drawn where the table is.
13. **Its stylesheet comes after its start-up.** Obsidian adds a plugin's `styles.css` only after its `onload` (`loadCSS`), on a reload as at start-up. So with the switch on, the plugin draws no table until its stylesheet is in: `src/own-table/styles.css` sets `--selectable-tables-styled` on the body, and `whenStyled` in `preview.ts` waits for it. Drawn without it, the hidden probe beside the note took room, the note narrowed and every table was laid out again, and Obsidian's own editor code, which measures in each update, kept that chain going without a break, so the stylesheet never got its turn: a reload with a wide table in view froze the window until its renderer ran out of memory (STA-80).
14. **A right-click's menu.** The plugin's table has no menu of Obsidian's, so Obsidian's editor would show its own, from its `onContextMenu`. That handler waits for Electron's context-menu event, then gives up if the event's default has been prevented, so a `Menu.forEvent` from a listener on the note's content (`tableMenus`) is the only menu shown, as over Obsidian's table. *Own 70* checks that one menu shows. On a phone or tablet, Obsidian turns a long press, 800 ms, into a `contextmenu` event on what's under the finger, from a `touchstart` listener on the window, so the same listener shows a cell's menu there.
15. **Its handles' and buttons' look.** Obsidian's `app.css` styles `.table-row-drag-handle`, `.table-col-drag-handle`, `.table-row-btn` and `.table-col-btn` inside a `.cm-table-widget`, its cells `position: relative`, and its `.table-wrapper` too: hidden, and shown on hover on a computer; on `is-mobile`, the handles only in cells marked `mod-active-row-handle` and `mod-active-col-handle`, and the buttons only in a widget marked `has-focus`; while a handle is held, `is-dragging` on the widget hides the others. Its blue line is `.table-drag-target` with `mod-row` or `mod-col`, positioned in the widget. So the plugin's copies of them take Obsidian's look and a theme's.
16. **A range's look.** Obsidian's `app.css` draws a range of cells from classes on its cells, inside a `.cm-table-widget`: `is-selected` tints a cell with `--table-selection` by an `::after` that reaches over its borders, and `start`, `end`, `top` and `bottom` give that `::after` the frame's border, `--table-selection-border-width` in `--table-selection-border-color`, on the range's edges, rounded at its corners (read from 1.15.1's `selectCells`). So the plugin's range takes Obsidian's look and a theme's. *Own 111* checks the frame and the tint from computed styles and the window's picture.

**The keys on it (STA-80).** The navigation layer runs on the plugin's table with the rules it has on Obsidian's, and reads the table from the plugin, not the page:

- **Which table** comes from the plugin's list of the note's tables (`ownTables` in `layout.ts`, given by `own-table/index.ts`), whole, so the keys never see the seams between blocks: CodeMirror's `lineBlockAt` would give one block of 100 rows. Where the language copy isn't in place, a note's tables are Obsidian's, and the layer reads CodeMirror's blocks as before. The unit tests run every key test again with each table split into a block per row (`decide-blocks.test.ts`).
- **The selected cell** is drawn by the plugin's table (`markCell` in `model.ts`) whenever its row is drawn, so it stays outlined as its row leaves the page and comes back. Showing a cell scrolls the note, never the cell, since `scrollIntoView` would scroll the box that clips the table: a drawn row from its rect, sideways through `showSideways`, and a row not drawn, such as row 2,000 after Cmd+↓, by its estimated place first. The scroll's own measure then draws the rows there, and the cell is shown from where it's really drawn, before the frame is painted.
- **Rules only on the plugin's table** (`Layout.ownTables`): a tap of ↑ or ↓ beside a table stops on it and selects it, and the next goes on to the line beyond at the caret's place across, kept as the selection's `goalColumn`. A held key's repeats pass, read from the keydown by an `any` binding, and Vim's keys pass too. Enter on a selected cell opens it, in any table, since the plugin writes the cell's text itself. Obsidian keeps two guards for its own table only (read from 1.15.1: they look for its widget, and do nothing without one), so the plugin keeps them here: Backspace at the start of the line below selects the table, and an edit that leaves text right above a table puts a line break back at its start, in the same step (`blankLinesAbove`). Delete at the end of the blank line above does nothing, and Backspace at its start, under text, moves the caret up.
- **The caret rule:** a selection put inside a table's text by anything but a key or a press, such as closing Find, a Search pane result, Undo or another plugin's command, selects the table and the cell holding it (`caretInTable`), in a step of its own right after the update. Never during a composition or while Vim is driving.
- **A range of cells (STA-14):** Shift with an arrow grows a range from the selected cell, a drag across cells makes one (*Dragging across cells*, below), and Shift with a jump (Cmd+↑/↓/←/→, Home, End, Page Up and Down, Cmd+Home and End; Ctrl with Shift and an arrow on Windows and Linux) stretches it to the table's edge that way, along the row or column. `selectRange` in `cells.ts` keeps it as the cell it started from (`anchor`) and the cell moved to last (`selected`), which the note keeps in view, clear of what pins, and which Enter opens, Escape goes back to on its own, and Tab, the plain arrows and the commands start from: a plain arrow ends the range on its corner that way, its top left or its bottom right, as Obsidian's range does. A range of one cell is that cell selected, so the edit guard, typing below the table and Delete, Cut and Paste doing nothing are the selected cell's. No move dispatches. The table draws it (`markCell` with an anchor in `model.ts`) with Obsidian's classes for its own range (item 16 above, `range.ts`), on the rows in the page as they're drawn, touching only rows whose part of the range changed, and `pins.ts` on the pinned copies of its cells; the outline of a selected cell doesn't show. Where anything pins, the frame sits inside its cells. Copy puts the range on the clipboard as Obsidian's range copies it (1.15.1's `copySelection`): the Markdown table as `text/plain` and `text/markdown`, every cell at its whole column's width (`copyRange`, through `readTable` and `writeTable`), with the freeze mark left out; Obsidian's `<!-- obsidian -->` marker then the Markdown rendered by `MarkdownRenderer` as `text/html`, the marker being what has Obsidian's own paste take the Markdown; and `obsidian/table`, each cell's text and each column's alignment, which a paste into Obsidian's table reads. Obsidian's table, the fallback, keeps Shift with an arrow doing nothing on a selected cell. *Own 110* to *Own 120* check it, each against the switch off where Obsidian has the same: the drawn classes against the range after each key, on the copies too, the frame in the window's picture, Copy's four forms against Obsidian's copy of the same range, a paste into a note, the keys on a range, Table 2000 by 12 stretched to its corner, and 60 seeded random steps; `window.__checkRangesOnly`, with `__checkOwnOnly` and `__checkCellsOnly`, runs only them.
- **Find:** Obsidian's Find marks its match with a mark decoration of class `obsidian-search-match-highlight`, from a field, and the Search pane its result with `is-flashing`; the table's blocks hide both, so `index.ts` reads them from the decorations facet on any transaction with effects, and the table draws them in their cells (`matches.ts`): on the matched words where the cell draws them as typed, else on the whole cell. Find's close puts the selection on the match, and a Search pane result a caret at its start, both with no user event, and the caret rule takes them.

Items 1 to 8, 11, 14, 16, 20 and 22 of the list above, and 9's clause on Obsidian's own moves between cells, hold for Obsidian's table only; the check script's sections before *Own* run with the switch off, as the control.

**Editing a cell (STA-81).** A press on a cell, or Enter on a selected one, opens it in Obsidian's own Markdown editor, borrowed (`cell-editor.ts`), inside the drawn cell, with the drawn text hidden as Obsidian's cell hides it (item 8 of the first list). One cell is open per note (`openCells` in `layout.ts`). The note's text always wins (`open-cell.ts`):

- **Each change in the cell goes to the note at once,** one change in the note for each, with the change's user event, so the note's history groups typing as for Obsidian's cell, and only the characters that changed: a write over the whole cell had Undo restore a range whose start is past its end, which crashed the spike. A pipe is written `\|`, and a line break `<br>` outside code (`toCellEditor` and `toCellSource` in `table-text.ts`, one set of rules both ways). A table Obsidian wrote is padded as Obsidian pads it, read from 1.15.1's `updateCell`: its column as wide as its longest text and two spaces, every row's cell in it and the delimiter row written again when that changes. Any other table keeps its spacing, and only the cell changes, its pipes kept while the text fits, with a space kept after a backslash at its end, which would escape the pipe; a short row gets the cells it lacks (`cell-write.ts`). Obsidian's cell doesn't trim a cell as it closes either: it only marks its own model malformed.
- **The note's selection follows the cell's caret,** without scrolling, with `writesCell`, which the check on key moves and the caret rule leave alone. Obsidian's editor commands act at the note's selection, as for its own cell (Cmd+B, Cmd+K). A change that lands right inside the open cell's text is taken into the cell and written as the cell writes, escaped and padded (`reconcile`, a transaction filter), as Obsidian's table takes it into its open cell: so Insert horizontal rule writes `<br><br>---<br>` rather than splitting the row, and Bold keeps the column's pipes in line.
- **A change from anywhere else** (Undo from the cell or the note, Sync, a second pane, another plugin) comes into the cell, with its caret where the note's selection is, only after a composition in the cell ends. Such changes come often: on a long note, Obsidian's parser sends one, with no text, about 120 ms after each key. A space typed at the cell's end is only padding to the note, which trims it from the cell's text, so while the cell's text stands, the note's selection is read back by the cell's own text, and a caret after that space stays after it (Brian's hand check, 11/21). A selection that leaves the cell closes it, and in another cell of the table the caret rule selects that one. A cell whose row went in a rewrite of the table opens again in the same column of the row its line went to (`movedRow` in `cell-write.ts`), else at the same row: Sync and a second pane send a row put in or taken out above the cell as one change that rewrites the cell's line too, and the cell stays in its row's text, where Obsidian's own table closes it (STA-106). A table found anew is matched by where it starts, then by its place among the note's tables. A redraw of the open row redraws its other cells in place, never moving the row or the cell, which would take the keyboard from the editor; for the same reason the open row stays in the page however far the note scrolls, among spacers of its own, and the cell takes its focus back, without scrolling, when CodeMirror puts its block back in the page or moves it into a new box around a table's blocks. A rewrite that takes the cell's row gives the note the keyboard; the cell's own focus events say whether it had it, since an editor out of the page no longer does.
- **Its keys,** as Obsidian's cell has them, read from 1.15.1, while no suggestions show: ← and → (and Cmd+←/→) at the text's ends to the cell before or after, ↑ and ↓ on its first or last line drawn to the cell above or below, out of the table at its edges to the start of the line beyond; Tab and Shift+Tab to the next cell with its text selected, Enter to the cell below, and at the table's end nothing, held or not (STA-83 adds rows); Cmd+Z and Cmd+Shift+Z run the note's undo and redo, as Edit › Undo and the palette's do. Escape goes through `escapeCell`: the cell closes and is selected, and Escape again selects the table. The jump keys close it the same way and jump (`cellJumpKey`).
- **The private calls,** in `cell-editor.ts` only, each checked before use (`missingPiece`): (1) the base Markdown editor class, the first class up from `MarkdownView.editMode` that has `editTableCell`, made with `(app, containerEl, owner)`; (2) its `set`, `cm`, `editorEl`, `sourceMode`, `buildLocalExtensions`, `onUpdate` and `destroy`, besides the public `load` and `unload`; (3) the `activeCM` getter of `editMode` and the `inTableCell` getter of the note's `Editor`, answered for the open cell with instance getters, so `focus` and `exec` reach it and Toggle checkbox, lists, quotes and callouts leave the table's row alone, taken off as the plugin unloads; (4) `app.workspace.editorSuggest.isShowingSuggestion()`, so suggestions take the cell's keys first; (5) `window.CodeMirror.getMode` with `hypermd` and the options of Obsidian's own cell's language, since the base class adds no Markdown language and without one nothing renders. Relied on, not called: Obsidian loads plugins' editor extensions into the borrowed editor, the plugin's own included, which stand aside there (`inOwnCell` in `layout.ts`; `language.ts` gives that editor no copy).
- **The fallback:** at the first cell opened after Obsidian starts, a missing piece, or an error building the editor, has cells open in a plain CodeMirror editor of the plugin's own until Obsidian restarts, and a notice says so once. Markdown shows as text there until the cell closes, with no suggestions or paired brackets; keys, writes, undo and input methods are the same code, and it gets the same `inTableCell` answer while those getters exist. The preview command *Open cells in the plain editor (preview)* forces it.
- **How the check script notices:** *Own 50* to *Own 64*, run with the switch on, open cells with real presses and keys through the window's debugger: the editor is borrowed, Markdown hides as you type, suggestions take the keys first, the note's editor answers for the cell, the keys' landings, the table's end, Escape's two steps, clicking out, Stock's escaping and padding, undo from the cell and the note, edits from elsewhere and rewrites, input methods, scrolling away, the fallback forced and each private piece taken away in turn named, the right-click menu, then 3 × 200 seeded random steps. `window.__checkCellsOnly`, with `__checkOwnOnly`, runs only them. `.dev/measure`'s `measure-sta81.js` times the cell against Stock, and `compare-sta81.js` plays the same input in both and lists what differs; `.dev/themes/sta81/open-cell.cjs` compares an open cell with Obsidian's under the default theme, Minimal and Baseline, headless.
- **A press** puts the caret where it landed in the drawn text, counted in visible characters and found again in the editor's drawn text, where Live Preview hides the Markdown the same way, else where the press is in the editor. On a phone the editor takes the focus inside the tap's own handler, which is what has iOS show the keyboard.

**Frozen rows and columns (STA-91), on a computer.** `pins.ts`, with its sums in `pin-sums.ts`. On a computer no box scrolls the table sideways (item 12), so rows stick to the note with plain `position: sticky`, where the scroll runs, and nothing runs as the note moves. The mark is read from the header line on each refresh, as for Obsidian's table.

- **One block:** the real `thead` sticks, and each frozen row under it, at `--selectable-tables-own-pin` (the scroller's top padding, negated, so rows pin at the pane's top, moved up to the start of the device pixel the pane's top falls in: where a pane starts part way into one, as under Minimal and the default theme at 78.09 px, that row of pixels showed the rows passing under; then a grip's height lower, the band below) plus the rows above. Sticky rows in one table can't leave together: each is held by its own section's end, so in the table's last few pixels a frozen body row slides under the header before both leave.
- **More blocks:** each block draws a copy of the frozen rows, rendered from their text (`render`), on a rail the block clips (`overflow-y: clip`, `overflow-x` left visible so the table's slide still clips at the box). The copy has no height and sticks; the rails' ends (`railOf`) make one block's copy slide out as the next one's slides in. The last block's rail ends the rows' height above the table's end, so they leave with it. The copy follows the table's slide by the same animation. It also carries a transform animation that moves nothing (`selectable-tables-still`, on the note's scroll): Chromium paints only what of a clipped sticky box was inside the clip when it last painted, and doesn't paint again as it sticks, so the next block's copy slid into view across a seam with its frozen column's cells drawn but their text missing, for a pinned rows' height of scrolling (Brian's hand check, 11/22). Only the screen's own frames show this (`Page.startScreencast`); `capturePage` and the page's state are right.
- **The band (STA-116):** rows pin a grip's height below the pane's top (`--table-drag-handle-size` in device pixels, 16 px, `--selectable-tables-band` on the editor), so the pinned header's column grips, which sit just above it, stay in the pane. The pinned header draws the band as its `::before`, under its grips: the real one, each block's copy and the strip's and the corner's, so it moves sideways with what draws it. It's painted with what shows behind the table, and a press on it selects the table. On the first block it grows from the header's top by `scaleY` as the table's top passes where rows pin, on the rows' timeline, so it covers just the rows passing up there: at rest it would cover the selected table's frame. A later block's lies above the block, which clips it, until the block's top passes where rows pin. **Editing rows and columns (STA-97).** The right-click menu's *Row* and *Column* submenus and its two sorts, and Obsidian's 15 table commands, on the plugin's table, from a selected cell or an open one. `table-edits.ts` works each edit out from the text alone, as Obsidian's table writes it (read from 1.15.1's `insertRow`, `moveRow`, `removeRow`, `insertColumn`, `moveColumn`, `removeColumn`, `setAlignment`, `sortByColumn` and `dispatchTable`), and `table-commands.ts` runs it:

- **The text.** Obsidian reads the table into cells (trimmed, a row of only dashes dropped, a short row filled, extra cells adding columns; the plugin's table draws a row of dashes, so a cell's row is counted past it) and each column's width, its longest text and two spaces, then writes the whole table again at those widths after the edit. It doesn't work the widths out again, so Delete row leaves a column as wide as it was, and a table spaced by hand comes out tidied. Only the lines that differ are written, each in place, in one transaction with `writesTable` and `isolateHistory`, so a caret on another row stays and Undo takes the edit back alone. A row added or taken out is a line put in or taken out with its line break (`alignedChanges`, from `from` on the edit): CodeMirror keeps the note still by a place in its text, and one change from the first line that differs to the last, as the first edit of a table spaced by hand would make, moved that place to the change's edge, and the rows on screen jumped by hundreds of pixels on a long table. The blank line above a table isn't put back for these writes (`blankLinesAbove` skips `writesTable`), since a new header goes in at the table's start. Deleting the last row or column takes the table away, as in Obsidian.
- **Sort** compares what cells show, read from their Markdown (`shownText`), since a table of 2,000 rows can't be drawn to read it, with Obsidian's collator: case and accents aside, numbers in number order, the header kept, equal rows in their order.
- **The freeze mark** stays in the header: an edit that takes it out puts it at the start of the new header's first cell, and a copy of the header row or of the mark's cell doesn't copy it.
- **The cell afterwards** is where Obsidian puts its focus. A new row's or column's cell opens; after any other edit an open cell opens again in its new place, and a selected one stays selected. An open cell closes first, through `escapeCell`, so the edit is the only change. The cell is selected, or opened, once its row is drawn from the new text (`afterDraw` on the model), without scrolling first: right after the edit, the row drawn there can still be the one from before, and after an edit to the header no row is drawn until the next measure, so showing the cell at once would scroll the note to its row's estimated place.
- **Tab on the last cell and Enter on the last row** of an open cell add a row below, on a fresh press only: the cell's keymap reads `event.repeat`, so a held key stops at the last cell. Shift+Tab on the first cell does nothing (Obsidian adds a row above).

Estimated again, the rows on screen would move.
- **The menu.** A right-click on a cell that isn't open selects it first, so it shows which cell the menu is for; an open cell's empty space keeps it open. `tableMenus` and `cellMenu` in `freeze-commands.ts` take the items from a hook `preview.ts` sets (`setTableItems`), so a release has none. - **The commands** are named as Obsidian's, without its *Table:* prefix, and are offered only with a cell of the plugin's table selected or open. Obsidian's own need its cell, so they stay hidden; a hotkey set on one of them doesn't reach the plugin's.

**Drag handles and + buttons (STA-98).** As Obsidian's table makes them (read from 1.15.1's `render` and `createDragHandle`), in `grips.ts`: a handle for dragging a column in each header cell, then one for dragging a row in each row's first cell, the header's included, each copied from one made per window, since rows are drawn often; and in each block's `.table-wrapper`, a + below the table, shown on the last block only, and a + at its side, which runs every block's height with no border at the seams, so the + icon sits in each block's middle. **Matching a theme (STA-88).** What it took to match Obsidian's table within a pixel under the 21 themes:

- The hidden table `metrics.ts` reads sits in a hidden stand-in for the note's content, beside it with its classes (`selectable-tables-probe-content`), so a theme's rules for a table in the content reach it, Typewriter's padding say, and it takes the width a table has there, as under Minimal's line width. Put in the content itself, it would be an edit to CodeMirror.
- A theme's font loads once text first uses it, after the plugin may have measured with the font standing in for it, and Obsidian sends nothing then: `preview.ts` lays tables out again on `document.fonts`' `loadingdone`, and the text widths kept are forgotten.
- A change of look makes every editor's sizes out of date (`lookChanged`), with the switch on or off: forgotten only in editors the plugin was drawing in, a theme changed with the switch off left tables laid out with the theme before once it was back on (Brian's hand check, 11/20; `Own 17`).
- Where a theme keeps every space (`break-spaces`, as the default theme does), a line breaks only after its spaces, so a word not last on its line takes its space with it, which sets a column's narrowest width. A word runs on across styled spans until a space.
- Widths are kept to a 64th of a pixel, as the browser lays a table out: whole pixels moved the lines after each column. Between their narrowest and widest, Chromium shares the room by how much more each column wants, and WebKit, on an iPhone or iPad, column by column by how wide each wants, taking any excess back from the last (`shareAsWebKit`).
- Joined borders lie half in each cell beside them; a theme that keeps them apart has each cell hold its own whole, and the table's own borders and spacing count too. A theme that stretches tables, Typewriter or Baseline, has the room left shared out by how wide each column wants.
- A theme's border on the table itself is drawn only at the table's ends, not at its seams. The blocks in a box are `fit-content`, not `max-content`, since a theme that makes every table 100% wide (Border, Tokyo Night) gave a table of percentage width a million pixels of max-content.
- A picture or a player has no size in its text. Once it has one (a picture's `load`, a video's `loadedmetadata`, a player at once), `measureContent` measures a copy of its cell alone in a hidden table, squeezed and spread, as the browser does a cell, and the columns are fitted again, without the note moving. The size is kept by the cell's text, and measured again after a change of look.
- An empty cell holds a line break, as Obsidian's does, so a row of empty cells is a line tall.

The misses left, each in one theme, are listed in STA-88's PR. A theme's own table settings (row numbers, AnuPpuccin's table styling) aren't matched yet: STA-94.

**Timing** is `.dev/measure`'s `measure-real-table.js`, and for blocks `measure-blocks-real.js`, run with each build to compare; their README says how. Blank bands on hard flicks are `measure-flicks.js`'s: it counts them in the frames the screen gets, since `capturePage` waits for the page and never sees the screen run past the drawn rows. A real hard flick runs far past 6,000 px/s, so time 12,000 to 40,000, interleaving what you compare, since runs vary widely. And time it with an accessibility client running, as anyone using a screen reader or a tool that labels what can be clicked has it: Obsidian then updates its accessibility tree for the rows each draw adds, 18 to 37 ms a time, which is most of what still lets the screen outrun the rows. `@codemirror/language` is a dev dependency for its types only, pinned at 6.13.1 with the same `@codemirror/state` as `obsidian`; Obsidian 1.15.1 bundles at least 6.12.3 (its bracket matcher and its stream parser's chunk size match that version), and the renderer uses only what 6.0 already had.

## Before every push

`npm run build` (typecheck included, and the check that a release leaves the plugin's own table out), `npm run lint` and `npm test` must pass. CI runs the same on Node 22 and 24.

`npm run lint` runs what the directory's scan checks, so a release's scorecard holds no surprises:

- **ESLint** with `eslint-plugin-obsidianmd`.
- **Obsidian's CSS rules** (`stylelint-config-obsidianmd`) on `styles.css` and the preview's `src/**/*.css`, failing on any warning. Their warnings, such as `:has()` and `!important`, are what the scan reports. The formatting rules the config inherits, which the scan doesn't report, are off in `stylelint.config.mjs`.
- **A typecheck of `src` without `@types/node`** (`tsconfig.scan.json`), as the scan's lint runs. Node's types declare newer methods, such as `Array.prototype.at`, than our `lib` has, so the usual typecheck passes them and the scan reports them.
- **`scripts/check-version.mjs`:** `package.json`, `manifest.json` and `versions.json` name the same version. The release workflow runs it with the tag too, and makes no release if they differ.

When `eslint-plugin-obsidianmd` or `stylelint-config-obsidianmd` publishes a new version, update to it before the next release, since the scan may already apply it.

## Releases

Every release gets one set of release notes, written when we're ready to release. `CHANGELOG.md` holds only released versions, so there's no Unreleased section, and PRs don't add to it: this replaces the usual changelog entry in each PR. The README still changes in the PR.

The notes read like Obsidian's own, for an average user:

- **One opening sentence** on what the release brings.
- **Three headings, in this order: New, Improved, Fixed.** Leave out any that's empty.
- **Short, plain bullets:** one line each, on what the user will notice, in their words. Name keys and buttons, not internals: no issue numbers, function names or Obsidian's internals, and no reasons they don't need.

To release:

1. Draft the notes in `.dev/release-notes.md` in the main clone, which git ignores, from what merged since the last tag (`git log <tag>..master` and those PRs' descriptions). Keep anything already in that file.
2. Open that file in Zed for Brian (`zed <path>`; he's asked for this each time, so it needs no asking first). He edits it there and saves, and his words are the notes. Wait for his OK.
3. Add them to `CHANGELOG.md` as `## <version> (<date>)`, bump the version, and merge that.
4. Tag the release. The release workflow builds a draft on GitHub with no notes.
5. Paste the same notes into that draft, and publish. Obsidian's plugin page links to it, and update checkers show it. Then empty `.dev/release-notes.md`.

## Working in Obsidian

- Drive it through the CLI: `obsidian vault="Selectable Tables Test" eval code=...` and `dev:cdp`. The `obsidian` module can't be loaded from that eval; `window.electron.ipcRenderer.sendSync('version')` gives the app's version. `document.execCommand` skips `beforeinput`, so test typing with real key events (`dev:cdp method=Input.dispatchKeyEvent`).
- An `obsidian://open?path=` link to a folder Obsidian doesn't know raises a system error box that blocks Obsidian until someone clicks OK. To open a vault folder, send `window.electron.ipcRenderer.sendSync('vault-open', <path>, false)` from an open vault, as the vault switcher does; `vault-remove` takes it off the list again.

- Anything that opens Obsidian takes over Brian's screen: ask first, with what opens, for how long, and whether he must keep off the keyboard.
- Only ever the test vault. Never Brian's own vault, and never restart Obsidian without asking (a restart also installs a pending Obsidian update).
- Obsidian's own code is in `~/Library/Application Support/obsidian/obsidian-<version>.asar`. To read it, extract `app.js` with a small asar reader (a 16-byte header, then a JSON index of offsets) into a scratch folder, never into the repo.
