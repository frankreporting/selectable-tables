# The plugin's own table: rows, columns, drags and a range's menu

Moved here from `CLAUDE.md` on 2026-11-26. This file loads by itself when a session opens a file under `paths`. When a change alters what it says, update it here.

**Editing rows and columns (STA-97).** The right-click menu's *Row* and *Column* submenus and its two sorts, and Obsidian's 15 table commands, on the plugin's table, from a selected cell or an open one. `table-edits.ts` works each edit out from the text alone, as Obsidian's table writes it (read from 1.15.1's `insertRow`, `moveRow`, `removeRow`, `insertColumn`, `moveColumn`, `removeColumn`, `setAlignment`, `sortByColumn` and `dispatchTable`), and `table-commands.ts` runs it:

- **The text.** Obsidian reads the table into cells (trimmed, a row of only dashes dropped, a short row filled, extra cells adding columns; the plugin's table draws a row of dashes, so a cell's row is counted past it) and each column's width, its longest text and two spaces, then writes the whole table again at those widths after the edit. It doesn't work the widths out again, so Delete row leaves a column as wide as it was, and a table spaced by hand comes out tidied. Only the lines that differ are written, each in place, in one transaction with `writesTable` and `isolateHistory`, so a caret on another row stays and Undo takes the edit back alone. A row added or taken out is a line put in or taken out with its line break (`alignedChanges`, from `from` on the edit): CodeMirror keeps the note still by a place in its text, and one change from the first line that differs to the last, as the first edit of a table spaced by hand would make, moved that place to the change's edge, and the rows on screen jumped by hundreds of pixels on a long table. The blank line above a table isn't put back for these writes (`blankLinesAbove` skips `writesTable`), since a new header goes in at the table's start. Deleting the last row or column takes the table away, as in Obsidian.
- **Sort** compares what cells show, read from their Markdown (`shownText`), since a table of 2,000 rows can't be drawn to read it, with Obsidian's collator: case and accents aside, numbers in number order, the header kept, equal rows in their order.
- **The freeze mark** stays in the header: an edit that takes it out puts it at the start of the new header's first cell, and a copy of the header row or of the mark's cell doesn't copy it.
- **The cell afterwards** is where Obsidian puts its focus. A new row's or column's cell opens; after any other edit an open cell opens again in its new place, and a selected one stays selected. An open cell closes first, through `escapeCell`, so the edit is the only change. The cell is selected, or opened, once its row is drawn from the new text (`afterDraw` on the model), without scrolling first: right after the edit, the row drawn there can still be the one from before, and after an edit to the header no row is drawn until the next measure, so showing the cell at once would scroll the note to its row's estimated place.
- **Tab on the last cell and Enter on the last row** of an open cell do nothing, tapped or held, and so does Shift+Tab on the first cell, where Obsidian's cell adds a row below or above (STA-9). Rows are added with the + below the table, the right-click menu and the table commands.
- **Row heights after an edit.** A row the edit rewrote but left with the same cells, padding aside, keeps the height it was drawn at (`drawnHeights` in `model.ts`), and so does each row when an edit to the header or the columns works the whole shape out again (`remember` and `startHeights`): by place with as many rows as before, else by cells. Estimated again, the rows on screen would move.
- **The menu.** A right-click on a cell that isn't open selects it first, so it shows which cell the menu is for; an open cell's empty space keeps it open. `tableMenus` and `cellMenu` in `freeze-commands.ts` take the items from a hook `preview.ts` sets (`setTableItems`), so a release has none. Over an open cell's text, the editor's own items come first, through `editor-menu`. The Row, Column and Sort items go in from a listener that runs as the event starts, as a cell's own listener adds them in Obsidian's table, and the freeze items as it ends: Obsidian's editor adds a link's items between, and its menu orders sections it doesn't know by when their items came, so a link's menu matches Obsidian's (STA-106). Submenus come from `MenuItem.setSubmenu`, which is private: without it the items follow a *Row* or *Column* heading in the menu itself.
- **The commands** are named as Obsidian's, without its *Table:* prefix, and are offered only with a cell of the plugin's table selected or open. Obsidian's own need its cell, so they stay hidden; a hotkey set on one of them doesn't reach the plugin's.
- **How the check script notices:** *Own 74* to *Own 81*, with the switch on: the menus against Obsidian's own with the switch off, on a cell, over an open cell's text and in an open cell's empty space below it; every item's text against Obsidian's, with Undo and Redo, and where the cell ends; the hand-spaced table; the commands from a selected cell and with none; Tab and Enter at the table's end adding nothing, tapped and held; the freeze mark in *Plants*; and Delete row, Move row down and Sort on *Table 2000 by 12*, timed. `window.__checkEditsOnly`, with `__checkOwnOnly` and `__checkCellsOnly`, runs only them.

**Drag handles and + buttons (STA-98).** As Obsidian's table makes them (read from 1.15.1's `render` and `createDragHandle`), in `grips.ts`: a handle for dragging a column in each header cell, then one for dragging a row in each row's first cell, the header's included, each copied from one made per window, since rows are drawn often; and in each block's `.table-wrapper`, a + below the table, shown on the last block only, and a + at its side, which runs every block's height with no border at the seams, so the + icon sits in each block's middle. They show by CSS alone (item 15 of the list in `own-table.md`). A press on a handle and a + go to `drag.ts` and `table-commands.ts` through `setTableControls`, which `preview.ts` sets, so the model needn't import the note's commands.

- **A drag** (`drag.ts`) runs Obsidian's frame loop: near the pane's top or bottom the note scrolls, and near the table's sides the table moves sideways (its bar on a computer), in a band of 16 px a device pixel, faster the deeper (`edgeScroll` in `drag-sums.ts`, Obsidian's helper's sums). It lands on the row or column the handle's middle is over, kept within the table, as Obsidian has it. The row being dragged can leave the page as the note scrolls, so the handle that moves is a copy, put in the first cell of the row under the pointer, and the other handles hide (`is-dragging` on every block); the landing comes from the table's heights, measured from the block nearest the pointer (`rowLayout`, `rowAtHeight` in `model.ts`), not from rows in the page, and a column's from its widths (`columnLayout`). Obsidian's blue line goes in the landing row's block, or in every block for a column. Each frame reads every place before it scrolls or writes anything, so it forces no layout of its own: 0.2 ms a frame, where reading after the scroll cost 1.5. Let go, `moveTo` writes the move as Obsidian's `moveRow` and `moveColumn` do (`row-move` and `col-move` in `table-edits.ts`), and selects the moved row or column as a range of cells, as Obsidian does with a mouse; after a finger's drag, the moved row's first cell or the moved column's header cell. Escape, a right-click, a cancelled pointer, or any change to the note, Sync's or a second pane's, cancels the drag. A touch keeps going to the element it started on, and in WebKit its events go nowhere once that's out of the page, as the pressed row is when it's drawn again or scrolls far off, so a touch is captured on the note's scroller at the press, and losing that capture cancels the drag. In the space a theme leaves between cells, a column lands on the nearer one.
- **A press on a handle** with a mouse or a pen selects its row or column as a range of cells, closing an open cell, from its first cell, which is the range's cell moved to last (`selectWhole` in `table-commands.ts`), so Escape goes back to it and the note is kept to it, never to a column's far end, as Obsidian's handle selects it (STA-118). It stays selected through the drag. A press that moves less than 4 px is a click, which leaves it selected and shows no menu, as in Obsidian; a right-click on a handle selects its row or column the same way (`gripItems`), where Obsidian's selects nothing, and shows its menu: its row's items, or Sort and its column's items, in the menu itself, with no freeze items (`tableItems` with a `grip`). A finger makes no range yet (STA-111): its press selects the row's first cell or the column's header cell, and a tap shows the handle's menu. A long press on a phone shows the menu once (`onMenu` ends the press).
- **The pinned header's grips** sit above it, in the band rows pin below (STA-116), so a column can be dragged, or its menu shown, with the header pinned: from the real header in a table of one block, from the copy of the block crossing where rows pin in a longer one, which maps to the real column. A pinned row's own grip, at its side, works too. Obsidian's frozen table, the fallback, pins at the pane's top, its grips above the pane.
- **The + buttons** write a row at the table's end, or a column at its end with no alignment, as Obsidian's buttons call `insertRow` and `insertColumn` (`row-end` and `col-end`), and open the new row's first cell or the new column's header cell. `runEditAt` runs them, and the drags, on the table itself, with no cell selected first, so the note doesn't scroll to one.
- **The scrollbar's room.** On a computer, a wide table's bar sat in the box's bottom padding, under the last row, where the + below is, and above it, since the bar is in the scroller. So while a table slides, its last block's bottom padding grows by the bar's 12 px (`dress`, and `blockHeight` for CodeMirror's estimate) and the bar sits at rest below the + (`readBar`): as a box's own scrollbar adds its height when scroll bars always show. Such a table's box is 12 px taller than Obsidian's with overlay scroll bars, the default on a Mac.
- **On a phone or tablet,** `paintHandles` in `model.ts` marks the selected or open cell's row's first cell and its column's header cell with Obsidian's classes, and every block `has-focus` while a cell is open, or selected on `is-mobile`, so its handles and buttons show as Obsidian shows them for its open cell.
- **Where it differs from Obsidian's table:** a finger's tap on a handle shows its menu; a table that slides is 12 px taller; in a table that runs right to left, each row's handle sits at the table's right, where Obsidian sets each cell's own direction on the cell, so a row whose first cell is empty or reads left to right gets its handle inside the table.
- **How the check script notices:** *Own 92* to *Own 99*, with the switch on, each against the switch off where Obsidian has the same: the handles' and buttons' places within 1 px and their hover, row and column drags in *Two report tables* writing Obsidian's text with its blue line, the menus, the + buttons, a phone's layout by `is-mobile` on the body, a drag cancelled by a second pane's change, row 3 of *Table 2000 by 12* dragged past row 250 with the note scrolling and column 2 to column 11 with the table sliding, timed per frame, the + below clear of the bar, and *Plants* with its header pinned, its grip for Bed in the pane, dragged and clicked as at the header's place, and Column 2's past row 300 of *Frozen table 2000 by 12*. `window.__checkDragsOnly`, with `__checkOwnOnly` and `__checkCellsOnly`, runs only them. `.dev/themes/sta88`'s `cases.cjs grips` adds the same cases with every handle and button shown, compared box by box.

**Dragging across cells (STA-35).** A press on a cell with the left button of a mouse or a pen, or in the open cell's text, goes to `cell-drag.ts` through `setTableControls`, as a handle's does, and becomes a drag once the pointer reaches another cell: until then a press that wobbles inside its cell is still a click on release. With *Click to select a cell* on, a press in the open cell, its text or its own space, never goes to `cell-drag.ts`, so its editor selects text however far the pointer goes (*Clicks*, in `own-table-keys.md`); off, its editor selects text until the pointer reaches another cell. The range is STA-14's (`selectRange`, with no scroll), so the keys, Copy and the edit guard act on a dragged range as on one from Shift+arrows, and the pointer moves the cell moved to last.

- **Its way in:** an open cell closes through `escapeCell`, the table is selected whole in one transaction, and the note takes the keyboard without scrolling, since the press's default is prevented. Moves after that dispatch nothing. The release's click, which the browser sends to what the two cells share, a row or the table's body, or outside the block across a seam, is swallowed in the same task, so no cell opens and the table isn't selected again.
- **The cell under the pointer** is found once a frame, from `elementFromPoint` and `cellAtPoint` in `model.ts`, a pinned copy's being its real cell and a rounded corner's gap the pinned cell beneath (`pressBeneath`): the cell right under the pointer, where one of the table's is drawn, else at the pointer kept a pixel inside the table's part on the screen (`lookAt` in `drag-sums.ts`). The pointer comes first since the point kept inside sits above a status bar floating over the pane's bottom, across the whole table's width, and a click on a row cut off there would reach the row above. Past the table's edge, the nearest cell in the pointer's row or column; in the band above the pinned rows, the pinned header. So a drag onto a pinned row takes that row at once, with every row between, as Brian decided on 11/23. Between cells or over a row not drawn yet, the row and column come from the table's heights and widths; between pinned cells the cell already reached stays.
- **At the edges** (`zoneScroll`): within 16 px a device pixel of the pane's bottom, or just under the pinned rows while they pin (the pane's top otherwise), the note scrolls, and within the same of the table's box's sides, or just beside the frozen columns, the table slides, at a dragged handle's speeds (`edgeScroll`), the fastest once the pointer is past the edge. A pointer on what pins scrolls nothing that way, and the note scrolls only while the table has rows beyond the pane that way. The frame loop runs only while the pointer moves or sits in a zone, and reads everything before it writes, so it forces no layout of its own: the cell is found before the scroll, and the next frame finds the one it brought under the pointer.
- **Shift with a press** extends from the range's first cell, the selected cell, or the open one, at once, and a drag from there moves the far corner. `onLeave` in `cells.ts` keeps the selected cell for a Shift+press on a cell of its own table. **Four quick clicks** (`detail` 4, from a capture listener on each block) select every cell, as in Obsidian's table: the first opens the cell, and the second and third select a word and a line in its editor.
- **Left alone:** links and tags, the handles and + buttons, the sideways scrollbar (in the note's scroller, outside the blocks), any button but the left, and touch: a finger scrolls as before (STA-111 holds a finger's range). Escape or a right-click during a drag stops following the pointer, and so does a change to the note from elsewhere, Sync's or a second pane's: the range keeps its rows and columns where they still are, and the release still opens no cell.
- **Where it differs from Obsidian's table:** no cell is open after a drag (Obsidian opens the pressed one, read-only); the edges scroll on a computer, which Obsidian's table does only for a finger; frozen rows and columns get the cells drawn under the pointer; and a finger makes no range.
- **How the check script notices:** *Own 121* to *Own 133*, with the switch on: Basil to Leave dry against the same drag on Obsidian's table, a click and a wobble, a click on a row cut off beside the status bar, Shift+click and a Shift drag, Copy, a drag out of an open cell's text, four clicks, presses left alone, Table 2000 by 12 held at the pane's bottom and top and at the table's sides, *Plants* with rows and a column pinned, deep in *Frozen table 2000 by 12* across seams, a second pane's change mid-drag, and a pointer move's work, timed. `window.__checkCellDragsOnly`, with `__checkOwnOnly` and `__checkCellsOnly`, runs only them.

**A range's menu and the grips' clicks (STA-118).** A right-click inside a range of cells of the plugin's table shows Obsidian's menu for its range (read from 1.15.1's `onContextMenu` with cells selected), from `range-menu.ts`: Cut, Copy and Paste on a computer, the Format submenu, Align left, center and right, Clear cells and Delete cells, with no freeze items. `tableMenus` in `freeze-commands.ts` checks whether the cell pressed is in the range (`inRange`) and asks for the items with `'range'`; a right-click outside the range selects that cell and shows its menu, as before.

- **Cut, Copy and Paste** call the window's Electron contents (`electron.remote.getCurrentWebContents()`, private, checked before use, left out where it's missing or on a phone), as Obsidian's range menu does. They send the browser's own clipboard events to the note, which Cmd+X, Cmd+C and Cmd+V already answer (*Clearing, cutting and pasting cells*).
- **Format** is Obsidian's submenu (1.15.1's `T5`), built by the plugin (`formatItems` in `formatting.ts`): each item calls the note's `Editor`, which hands formatting to the selected cells (*Formatting cells*). Each is checked when the range's first cell has it throughout, as Obsidian reads it (`bd`), from the stand-in table parsed by Obsidian's language, reading each token's classes through `tokenClassNodeProp`, which Obsidian's copy of `@codemirror/language` exports and CodeMirror's doesn't, so it's read by name, as `lineClassNodeProp` is. Without it nothing is checked. Highlight's colors are icons the plugin adds (`addIcon`), since Obsidian draws its swatch into a menu item's private icon element.
- **Align** sets each of the range's columns, to the start or end of the table's direction, and the range stays selected. It changes only the delimiter row, which no drawn row's text holds, so `shape` in `model.ts` draws every drawn row and the header again when the columns' alignment changes, the open cell's row in place, and the pinned copies are drawn again too (`alignment` on the pins' host). Before, Align from any menu or command wrote the text and the plugin's table kept drawing the old alignment until the note was opened again (Brian's hand check, 11/25). **Clear cells** empties the cells and never deletes rows or columns, each column keeping its width, as Obsidian's item writes the table at the widths it had, and selects the range's first cell. **Delete cells** is Backspace on the range. Each item acts only while the range it was shown for is still selected.
- **The grips** (*Drag handles and + buttons*): a press with a mouse or a pen selects the row or column as a range, kept through the drag, and the moved one is selected after; a click shows no menu, and a right-click selects the row or column too before its menu, which Obsidian's grip doesn't (Brian's hand check, 11/25).
- **Where it differs from Obsidian's table:** the native menu on a Mac has no Writing Tools item, which Obsidian's range menu turns on (`setShowMacWritingTools`, private); a finger's tap on a grip shows its menu.
- **How the check script notices:** *Own 167* to *Own 174*, with the switch on, Obsidian drawing its menus: the range's menu, its Format submenu and Highlight colors against Obsidian's own range's with the switch off, in *Seed trays*; each item's cells afterwards against Obsidian's range doing the same, each alignment as drawn, a column centered deep in *Frozen table 2000 by 12* drawn so in its pinned header copy, and each Format item's checkmarks once it's on; a right-click outside the range; the grips of *Two report tables* clicked, keyed and dragged; row 3's grip and Delete in *Table 2000 by 12*, timed, and a phone's tap. The menu's Cut, Copy and Paste reach the system clipboard, so the section saves it first and puts it back. `window.__checkRangeMenusOnly`, with `__checkOwnOnly` and `__checkCellsOnly`, runs only them; *Own 93*, *Own 94* and *Own 99* now expect a grip's click to select, and right-click it for its menu.
