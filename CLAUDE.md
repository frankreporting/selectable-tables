# Selectable Tables

An Obsidian plugin (`selectable-tables`) that makes a Live Preview table one block for the arrow keys: ↑/↓ pass it in one press, and ←/→ at its edge select it whole, like an image. Enter then selects a cell, and the arrows move between cells without opening them. `AGENTS.md` holds the generic Obsidian plugin rules (manifest, releases, API use); this file holds what's specific to this repo and overrides it.

## Where things live

- **Backlog:** the Linear team **Selectable Tables** (key `STA`). Plans and test plans are Linear documents on their issue. There are no area labels yet: every issue runs alone, except a spike (see *Parallel work* in the global `CLAUDE.md`).

- **Tests:** `test/*.test.ts`, bundled by `scripts/test.mjs` with esbuild and run by Node's test runner. Tested code must not import `obsidian` as a value (the package is types only), so keep decisions in modules that take plain CodeMirror state.

- **Timing scripts:** `.dev/measure` in the main clone, ignored through `.git/info/exclude`, so they exist only on Brian's Mac. - **Theme checks:** `.dev/themes` in the main clone, ignored the same way, holds Obsidian's `app.css` and themes' CSS, and runs with no Obsidian open. `compare.cjs` draws a table unfrozen and frozen, marked by a clone's own `DrawnTable`, and compares their pixels at rest, then with rows pinned and the table scrolled sideways; with `BASE=<clone>` it also compares the frozen table against another clone's, 0.2.0 say. `timing.cjs` times marking a fresh table, against another clone. `open-cells.cjs` opens a cell as Obsidian does and compares its table's column widths and the cell's height under a clone's rules and another version's (`BASE`, master by default), theme by theme. `center.cjs` checks that a table a theme centers can still be scrolled back to its start, and that no table moves under any other theme, against `BASE`. Their headers say how to run them. Other themes come from their repos, listed in `community-css-themes.json` in obsidianmd/obsidian-releases.

## What the plugin relies on in Obsidian

These are Obsidian behaviors, not calls, so any Obsidian update can change them. `scripts/obsidian-check.js` tests them first; run it after each Obsidian update (its header says how).

1. A rendered table is one block widget in the editor, carrying the class `cm-table-widget`.
2. A caret inside a table's text opens a cell; a selection over the whole table opens none.
3. Focusing the note's editor closes an open cell.
4. A table's rows and cells on screen line up with its text: the header is row 0, the delimiter line has no row, and a short row is filled with empty cells.
5. A caret in a cell's text opens exactly that cell.
6. The selected table's tint is drawn on the table element, so the plugin can take it off while a cell is selected.
7. A press on a cell of a malformed table tidies it, which is what makes Enter work on it again. A table with only unusual padding stays as it is, and a press still opens its cells.
8. Opening a cell hides its rendered text's `.table-cell-wrapper` with an inline `display: none`, and builds a new `.table-cell-wrapper` beside it, holding the editor's own element, which holds `.cm-editor`. Closing the cell removes that box. `width-copy.ts` puts a copy of the rendered text right after the editor's element, and the copy holds the column's width. If this changes, no copy is made, and columns move again as in stock Obsidian.
9. Word jumps, Option+↑/↓, and the other moves a key can make across lines send the user event `select`. A click sends `select.pointer`, and Obsidian's own moves between cells send none.
10. Page Up/Down pass a drawn table from a line of text, since CodeMirror's page move steps out of block widgets. A table only becomes a block once Obsidian's parser reaches it, and a held key outruns the parser, so a table can still be lines of text when a move lands on it.
11. Obsidian binds Page Up/Down, Cmd+↑/↓, Ctrl+↑/↓ and Cmd+Home/End in a cell's editor as plain keys that hand over to the note, at a lower precedence than the plugin's keymap.
12. Vim puts `cm-vimMode` on the editor's scroller outside insert mode.
13. A table's widget is padded by `--table-drag-handle-size`, 16 px on a desktop and 24 px on a phone or tablet, and scrolls sideways itself, so it's the box `position: sticky` binds to, and frozen rows can't stick to the note's scroll.
14. Building a table anew empties its widget and keeps the widget, and a table that leaves CodeMirror's drawn range comes back as the same widget.
15. A table in Reading view sits in an `.el-table` box with its own scroll, so frozen rows can't stick there either.
16. Opening a cell focuses its own editor, inside the cell, so the note's content hears `focusin`. Obsidian's scroll to the cell runs right after that, in the same task.
17. On a phone with Floating navigation or Auto full screen on, both the default, a note in the main pane runs to the top of the screen, under the status bar and a fixed header. `--view-header-top-offset`, `--view-header-height` and `--safe-area-inset-top` say where those end, and `is-hidden-nav` on the body says the header has hidden. A tablet's note starts below its header.
18. On a phone or tablet, `body.is-mobile .app-container` takes `--keyboard-height` off its height, so the keyboard shrinks the note's pane, in steps: the toolbar above the keyboard first, then the keyboard.
19. Obsidian sends `css-change` once a change of look is in place: after switching light and dark, which toggles the body's classes first, and after loading a theme or a snippet, or changing fonts. The Style Settings plugin sends it after changing a setting, its body classes included.
20. An editor command gets the note's editor even while one of its cells is open: the cell's editor keeps the note's view as the active editor, and carries the note's `editorInfoField`, so `noteView` in `extension.ts` leaves cell editors out.
21. A right-click on a cell that isn't open shows Obsidian's menu for the table, made with `Menu.forEvent`, which prevents the event's default and gives the same menu to a later listener on that event: `tableMenus`, on the note's content, adds the freeze items there. A right-click in an open cell fires `editor-menu` with the cell's own editor, and the note's view as its info, whose editor is the note's. A right press on a cell doesn't open it. On a Mac, menus are native unless the vault says otherwise, and Obsidian builds those from the same items, so the check script has Obsidian draw them for its run.
22. A comment in a cell draws nothing, and the space typed beside it stays in the cell's text: Obsidian draws a cell by rendering `| <its text> | | - |` and taking the header cell's contents, and its cells keep every space (`--table-white-space: break-spaces`, in the default theme). Opening, editing or closing a cell empties and refills what's inside it and keeps the cell's element, so a class on a `th` stays until the table is built anew.

The plugin makes no private Obsidian calls. It reads only CodeMirror's public layout (`lineBlockAt`, `posAtDOM`, `moveVertically`), `editorLivePreviewField`, `editorEditorField` and `editorInfoField`, plus eight classes Obsidian puts in the DOM: `cm-table-widget`, to tell a cell's editor from a note's, `table-cell-wrapper`, to find an open cell's rendered text and its editor's box, and the open cell a command acts on, `mod-image-selected`, `has-selection`, which marks a dragged range of cells and keeps its right-click menu Obsidian's own, `table-row-drag-handle` and `table-col-drag-handle`, whose menus stay Obsidian's own too, `cm-vimMode`, and `is-mobile`, so frozen rows restart only on a phone or tablet. The right-click menu uses only the public `Menu.forEvent` and `editor-menu` (item 21). `styles.css` also reads item 17's classes and variables.

**How a table freezes.** The mark, `%%freeze 2 1%%` in any header cell, is the only record, so `freeze.ts` reads it when a table is drawn and when a change touches its header line, and nothing runs as the note scrolls. The commands write it before the first header cell's text, or over the mark already there, in one transaction. It carries `writesFreeze`, which the edit guard lets through on a selected cell, and `isolateHistory`, so the history never joins it with another edit and Undo takes it back alone. `@codemirror/commands` is a dev dependency for that one's type only, pinned to a version that takes the same `@codemirror/state` as `obsidian`: Obsidian gives plugins its own copy at run time. A header the mark can't go in safely, where a cell would lose text or the mark wouldn't read back, gets a notice and no change. The mark widens its column, and Enter opens a cell only in a table padded as Obsidian pads it, so a table Obsidian wrote is padded again that way (`rewrittenWith` in `table-text.ts`); any other table keeps its spacing, and only its header line changes. An open cell is closed and selected first, as Escape does it: Obsidian routes a change inside an open cell through the cell's own editor. Frozen columns are `position: sticky`, picked by `:nth-child`, because a class on every cell of a long table costs too much. Frozen rows can't stick (item 13), so a CSS scroll-driven animation on each row moves it with the note. It runs on the compositor, where the scroll does, so rows don't trail a real gesture, which a script's do. A script setting `scrollTop` runs on the main thread and hides that, so a timing check needs real input (`Input.synthesizeScrollGesture`), and only `capturePage` shows where rows are really drawn: page state reads correct when they aren't.

**A mark's space.** The commands write the mark with a space after it, `%%freeze 2 1%% Name`, and people type it that way. The mark draws nothing, but the space stays at the start of the cell (item 22), and in a column only as wide as "Name" it takes a line of its own, making the header row a line taller. So `freeze.ts` puts `selectable-tables-mark-cell` on every header cell holding a mark, frozen or not, each time it reads a table's header line, and `styles.css` gives that cell `white-space-collapse: collapse`: it drops spaces at a line's start and end and shows two in a row as one, as the 20 themes that set `--table-white-space: normal` do for every cell. Only the longhand, so wrapping stays as the theme set it: Minimal's and Baseline's no-wrap table settings still hold. An open cell's editor sets its own spacing, so the source shows as typed. Don't take the space out of the text instead: Obsidian's editor reads `#` as a tag only after a space, so a mark written right against `#tag` would stop it being a tag there, and marks already typed would keep the line. Reading view, where the plugin doesn't run, still keeps the space; STA-38 holds that.

Three things about frozen tables aren't obvious. When a theme collapses a table's borders, as the default theme does, a frozen table switches to separate ones, because collapsed borders stay behind when cells move, and its cells draw their own with Obsidian's variables. A theme with separate borders, Baseline say, already has each cell draw its own lines, so they're left alone. Sizes go on the rows, not the table, since a variable on the table restyles every cell; the one exception is a second or later frozen column's offset, which has to sit above all its cells, and changes only when a frozen column's width does. And the rows' animation runs 4000 px past the pane's top, with its easing holding them at the table's end. Without that it finishes as the table leaves the pane, and a finished animation isn't kept on the compositor, so a hard flick back into the table would draw the rows too low until the page caught up.

**A theme's colors.** Frozen cells have to be solid, since cells pass under them, so each is painted with what shows behind it unfrozen: the cell's own color, its row's, its header's or body's, the table's and the widget's, over the first solid color behind the table. `theme-paint.ts` reads these from computed styles, for the header's odd and even cells and the body's odd and even rows', since odd and even are what themes stripe by, and lays them as one-color gradients, so the browser blends them as it blends the elements and no color is parsed. Only opacity is read, to know where to stop. The read has to come before marking, since `styles.css` paints over the theme's colors, and reading a table that's just been drawn makes the browser work out its styles, which marking then has it do again: 2.4 ms on 50 rows, 81 on 2,000. So each editor keeps what it read by place, the classes of everything around the table less those that only mark focus and the like, and reads only the first table in each. A table too small to show every kind of row and cell, with a last row or cell among those read, or with a row under the pointer, is read but not kept. On `css-change` each editor forgets them all and, on its next frame, reads every frozen table on screen again: a popout window takes on the new look a moment after the event, and the font size slider sends one on every step. A color in the middle of a transition is read where it ends. A widget can outlive the plugin out of the drawn range, so one that still carries a freeze's marks when a new copy first sees it is cleaned from what's on it, before anything reads it. A theme's own picture behind cells, such as a texture, isn't kept, and nor are hover colors; STA-47 looks at what other themes still need.

**A cell's corners.** A frozen cell is solid only inside its shape, so where a theme rounds its cells, as Baseline does, rows passing under a pinned row would show at its cells' corners. The browser draws a cell's color, and its row's and its header's or body's, inside the cell's rounding, so at rest the corners show the table's color, over what's behind the table. `theme-paint.ts` reads that, starting at the table instead of a cell, into `--selectable-tables-corners`, and each pinned row lays it under its cells as an inset shadow. Only the row's shadow can do this: a color on the row is drawn inside each cell's rounding too, a pseudo-element on a row changes the table's layout, and one on a cell covers only that cell, since Obsidian positions the cells. Where nothing is rounded, the cells cover the shadow. What it leaves, all in STA-66: WebKit draws no shadow on a table row, so on iPhone and iPad the corners still show what passes, and a frozen header cell's corners still show the header cells that pass under it sideways, since those are in the same row, above its shadow. And the shadow makes the row solid, which hides anything the browser draws for the table outside the row: a theme that colors its header and rounds its cells gets corners a hair thinner at rest, and Sanctum's *Sticky headers*, which makes the header a table of its own with collapsed borders, loses the line under it at rest as well as pinned (STA-64).

Anything that has to keep up with a scroll must run where the scroll does: `transform`, `opacity` or `position: sticky`. An animated `clip-path` runs on the main thread, so a table scrolling sideways outruns it, and the clip snaps back on each frame. That's why the selected table's tint is kept out of the strip beside a frozen column by a sticky cover, not a clip. And a pinned row can't scroll to give its cell room, so a positive `scroll-margin` on it moves the note on every key: a cell there has a margin of -1px. For the same reason `scrollIntoView` does nothing on a frozen cell, so a key that moves up or left into one calls `backToStart` in `freeze.ts`, or the rows and columns beside it would stay hidden. `decide.ts` says which keys those are: moving along a pinned row must not scroll.

`backToStart`, `show` in `cells.ts` and frozen columns all assume a table's start can be scrolled to. A theme that centers a table in its box with flex breaks that once the table is wider than the box: it sticks out on both sides, and the side at the start is out of reach. Baseline does this with Table width on Auto (Center), and so does One Oracle Developer, built on it. So `styles.css` gives every table's box in a note the plugin runs in `justify-content: safe center`, which centers a table that fits and starts a wider one at the box's edge, and does nothing on a box that isn't flex or grid. It names no theme, and its five classes beat Baseline's four in either load order. A theme that centers with auto margins on the table instead, as Minimal does, already falls back to the start and needs nothing. MoreMonoColor sets the box's centering `!important`, so the rule can't win there, but its box shrinks to the pane and a wide table overflows only at its end. A theme that made the box flex to put tables at its start or end would get them centered; of 702 themes scanned on 11/4, none does. `.dev/themes/center.cjs` checks this headless.

**On phones and tablets.** A device without scroll-driven animations can't pin rows, so `freeze.ts` reads every table there as freezing nothing (`canFreeze`), and only marks the cells holding a mark, and its tables scroll as usual: an iPhone or iPad before iOS 26, and an old Android WebView. iOS 26.0 to 26.3 pass that check but run these animations on the main thread, so rows may trail the finger there, and CSS can't tell those versions apart. On a phone, `--selectable-tables-pin-top` in `styles.css` is where rows pin, from item 17: below the header, or the status bar once the header hides. It moves both ends of the rows' animation range, so the range's length, and `freeze.ts`'s sums, don't depend on it. The rows can't glide with the header, because a transition can't drive an `animation-*` property, in WebKit or Chromium. `app.emulateMobile` and the classes `scripts/obsidian-check.js` puts on the body show the layout, but scrolling and touch on a real phone are the only real test. WebKit runs headless through Playwright, with Obsidian's real `app.css`, for anything that doesn't need Obsidian itself.

**The keyboard on an iPhone, and frozen rows.** When the keyboard opens with the caret in one of a frozen table's cells, iOS's own copy of the rows' animation can stop following the scroll. It then draws the rows where they sit in the table, so they vanish from where they pin, while the page still has them pinned. A screen recording with Web Inspector's compositing borders on showed this on 11/2, so it's a WebKit fault; STA-43 holds the report for Apple. A caret in any cell triggers it, frozen row or not, and a caret on a text line hasn't. `restartRows` in `freeze.ts` clears it: on a phone or tablet, every change of the pane's height (item 18) starts the rows' animation again on a new timeline, in the resize observer's callback, before the pane is drawn at its new size. `selectable-tables-restarting` takes the timeline and the animation off for a moment, and the timeline comes back first. Reading a style in between brings both up to date without a layout, so a restart costs 0 to 1 ms on an iPhone, where a forced layout cost 6 to 19. Tried and dropped: restarting the animation alone made the rows blink, waiting 120 ms after the change let the fault show for about 0.13 s, and restarting only with the caret in a frozen row let it back in from a body cell. A known limit remains: the rows can flicker for a moment as the keyboard opens or closes, and the caret can drift inside its cell until the next key. The drift is probably the same kind of fault, since an open cell's editor gets a layer of its own inside the row. Tried on 11/1: moving the rows by `top` jitters constantly, sticky cells show gaps and take away the table's sideways scroll, and dropping `will-change` made no difference, so the rows keep it. A change here needs a control on the same build, since the fault is random enough that one run went 28,062 px between sightings. To load a new build on the phone: plugin off, force close Obsidian, reopen, plugin on.

**A cell stays clear of what's pinned.** Frozen rows and columns cover the cells that pass under them, and no scroll knows: the browser's and Obsidian's compare raw positions, and a cell's editor stops at a sticky cell, so typing in a frozen column's cell doesn't move the note at all. So `show` in `cells.ts` gives the cell scroll margins that reach past what's pinned, scrolls, and takes them off again, all in one go. It runs when a cell is selected, on the next frame after a frozen table's cell opens, and after a cell's editor scrolls to its caret, which an edit from Sync doesn't do. It also runs once a freeze command, Undo or Redo changes a header line with a cell selected (`showsCellAfter` in `decide.ts`), since Unfreeze sends a pinned cell back to its place in the table, which can be above the pane or off to its left. That one waits for the resize observer's callback after the new freeze is marked: the measure comes there, and so does it come after Undo and Redo's own scroll, which runs after everything a CodeMirror measure writes. An unfrozen table has nothing left to watch, so `freeze.ts` watches the pane anew, which sends a size at once. Undo's scroll takes the whole table into view, its far end on a long one, so Undo still moves the note when the cell was in view, and the cell ends at the pane's top. Keeping the note still there would mean replacing that scroll, with a check on every scroll into view, which is every keystroke; STA-55 holds that. Nothing else reads a scroll margin, so these sizes never go on the table, where a change would restyle every cell. `freeze.ts` measures them and leaves them in `pinnedTables`, in `cells.ts`, because `freeze.ts` already imports that file.

**The check on key moves.** `landing` in `decide.ts`, run as a transaction filter, is the one place that stops a key opening a cell: a move that sends `select`, other than a click's `select.pointer` or a search's `select.search`, and leaves one caret in a table's text selects the table instead, or is dropped from that same table selected or from a selected cell. So there's no list of keys to keep, and other plugins' move commands are covered too. Obsidian's Home, End and Cmd+←/→ send no user event, so the check can't see them; they can't cross a line, and the plugin's own bindings take them, with or without Shift, on a selected table or cell, and when a head sits on a table's edge. A browser-driven selection change gets `select` by default, so it passes through the check too. A big jump (Page Up/Down, Cmd+↑/↓, Cmd+Home/End, Ctrl+↑/↓) can land on a table that's still text, and a cell opens once Obsidian draws it; stock Obsidian does this too, on a held Page Down, but there the key carries on, while here Page Down in a cell stays in the table. So for these keys alone the check reads the table from the text and goes past it. Other keys don't, since text near the caret that reads as a table really is text, as in a code block. The check stands aside for what must still open a cell: a click, Enter's caret (`opensCell`), and a plain arrow the plugin left to Obsidian, which enters a table with no line beyond it. It also stands aside while Vim is driving, since selecting a table in normal mode would start Visual mode.

**A selected cell is a class, not a selection.** The note's selection stays on the whole table, and a move between cells dispatches no transaction, because each one walks the whole note in Live Preview and runs every plugin's listeners. So the edit guard is all that stops an edit meant for "the selection" from hitting the whole table. How edits reach it, read from Obsidian 1.15.0 and run on 10/30:

- Obsidian's editor commands, such as Toggle comment (Cmd+/), Toggle checkbox (Cmd+L) and Insert horizontal rule, send no user event. The table's own menus and + buttons send none either, and by then Obsidian has already changed the drawn table, so they must never be dropped: a press in the note takes the cell off first.
- A reload from disk, which is how Sync arrives, carries `userEvent: "set"`.
- A second pane on the same note arrives as a remote edit with `filter: false`, so it skips transaction filters.
- The freeze commands' own write carries `writesFreeze`, which passes.

**A caret doesn't repair a table; a press does.** Obsidian keeps its own model of a table's cells, and marks the table malformed when its text isn't what the table editor writes (uneven rows, other padding), or after closing a cell trims it, which changes the model without telling the note. A press opens a cell through `setCellFocus`, which rewrites a malformed table first. A caret landing in a cell skips that, and then typing can eat a pipe, or never reach the note. So Enter opens a cell only when `writtenByObsidian` in `table-text.ts` says the table's rows are exactly what Obsidian's editor would write. That check rebuilds the rows and compares them, on purpose: a wrong answer usually costs a click, while a check that tries to predict Obsidian's private flag can let a corrupting caret through. It can't see a stale model behind exact text, which undo can leave after a cell's trailing spaces are trimmed; a stock click does the same damage there. Don't bring back a keyboard repair by putting the caret on the delimiter line: it rewrites the table with the caret there, so undo goes back to that caret and Obsidian rewrites the table again, and undo can never get past it. Stock Obsidian has the corruption too when you arrow into a table.

**Never interfere with a running composition.** Dropping composed input in the guard, or moving the selection in `compositionstart`, leaves `view.composing` true for good. CodeMirror then ignores keys, and Live Preview stops rebuilding, so new notes draw no tables until the editor is replaced. An input method's first keydown comes before its composition, and that's the only safe moment to move the selection. Its `key` is the real letter on a Mac, `Process` on Windows and Linux, `Unidentified` on Android, and `Dead` for a dead key such as Option+E, so typing on a selected table or cell is told by `key`, with no `keyCode`. Left alone, a real input method on a selected table replaced the table with its first letter and put the rest below the next table (STA-46's probe, 11/2). With Japanese, Enter after Space leaves the text underlined, and a second Enter ends the composition, on a plain line too. Simulated composition (`Input.imeSetComposition`) must be finished with `Input.insertText`, or it freezes the test window the same way. Editor commands like Toggle line numbers are saved to the vault's tracked `app.json`, so a sweep of commands has to skip them.

A table is a block widget over text that reads as a Markdown table. At a note's start or right below the frontmatter, Obsidian draws a table with an exclusive start, and CodeMirror then reports the line as an empty text part plus the widget; `partAt` in `layout.ts` handles that. Obsidian keeps a blank line around the tables it makes, so a table with no line beside it only comes from a note written elsewhere, and isn't a case to plan or test for. `Table first`, `Table last` and `Properties then table` in the test vault are written that way by hand, so they don't show what real notes do. Unit tests use a fake layout (`test/notes.ts`), which can't show such details, so check layout changes against a real editor too. Since the check is the text, another plugin's block widget drawn over table Markdown would count as a table too.

`npm run build` (typecheck included), `npm run lint` and `npm test` must pass. CI runs the same on Node 22 and 24.

## Releases

Every release gets one set of release notes, written when we're ready to release. `CHANGELOG.md` holds only released versions, so there's no Unreleased section, and PRs don't add to it: this replaces the usual changelog entry in each PR. The README still changes in the PR.

The notes read like Obsidian's own, for an average user:

- **One opening sentence** on what the release brings.
- **Three headings, in this order: New, Improved, Fixed.** Leave out any that's empty.
- **Short, plain bullets:** one line each, on what the user will notice, in their words. Name keys and buttons, not internals: no issue numbers, function names or Obsidian's internals, and no reasons they don't need.

To release:

1. Draft the notes in `.dev/release-notes.md` in the main clone, which git ignores, from what merged since the last tag (`git log <tag>..master` and those PRs' descriptions). Keep anything already in that file.
2. Open that file in Zed for Brian (`zed <path>`; he's asked for this each time, so it needs no asking first). He edits it there and saves, and his words are the notes. Wait for his OK.
3. Add them to `CHANGELOG.md` as `## <version> (<date>)`, bump the version, and merge that.
4. Tag the release. The release workflow builds a draft on GitHub with no notes.
5. Paste the same notes into that draft, and publish. Obsidian's plugin page links to it, and update checkers show it. Then empty `.dev/release-notes.md`.

## Working in Obsidian

- Drive it through the CLI: `obsidian vault="Selectable Tables Test" eval code=...` and `dev:cdp`. The `obsidian` module can't be loaded from that eval; `window.electron.ipcRenderer.sendSync('version')` gives the app's version. `document.execCommand` skips `beforeinput`, so test typing with real key events (`dev:cdp method=Input.dispatchKeyEvent`).
- An `obsidian://open?path=` link to a folder Obsidian doesn't know raises a system error box that blocks Obsidian until someone clicks OK. To open a vault folder, send `window.electron.ipcRenderer.sendSync('vault-open', <path>, false)` from an open vault, as the vault switcher does; `vault-remove` takes it off the list again.

- Anything that opens Obsidian takes over Brian's screen: ask first, with what opens, for how long, and whether he must keep off the keyboard.
- Only ever the test vault. Never Brian's own vault, and never restart Obsidian without asking (a restart also installs a pending Obsidian update).
- Obsidian's own code is in `~/Library/Application Support/obsidian/obsidian-<version>.asar`. To read it, extract `app.js` with a small asar reader (a 16-byte header, then a JSON index of offsets) into a scratch folder, never into the repo.
