# The plugin's own table

Moved here from `CLAUDE.md` on 2026-11-26. This file loads by itself when a session opens a file under `paths`. When a change alters what it says, update it here.

## The plugin's own table

The plugin draws Live Preview tables itself, so a large table stays fast: only the rows near the pane are in the page, and a table of more than 100 rows is a block per 100 rows (`blocks.ts`), so CodeMirror counts only the blocks near the pane as on screen, and the parser and Live Preview do only that much after each key. Every note's tab gets it since the relaunch (BMT-84); before, it was behind a switch in preview builds. Its CSS is the second part of `styles.css`. The plugin's one setting, *Tab and Enter add a row* (*Editing rows and columns*, in `own-table-edits.md`), is saved in the plugin's data as `addsRows`; there's none for clicks (*Clicks*, in `own-table-keys.md`). Preview builds saved a click setting and their switch there, as `clickSelects` and `ownTables`, which are no longer read. `freeze.ts`'s pinning isn't loaded (the plugin's table pins frozen rows and columns itself, *Frozen rows and columns*, in `own-table-frozen.md`), and the navigation layer runs on the plugin's table (*The keys on it*, in `own-table-keys.md`): `tables.ts` puts the editor extensions in the array `main.ts` registers and calls `workspace.updateOptions()`.

**Where it doesn't draw, Obsidian draws its own,** as without the plugin, and the keys see no tables there (`viewLayout` in `layout.ts` gives no tables where `ownSpans` is null): canvas cards, hover previews and other editors outside a note's tab (BMT-95 brings the plugin's table there), and every note when the language copy can't be made, after an Obsidian update say. Then `tables.ts` shows `CANT_DRAW` once and empties the array (`use(false)`), so the plugin adds nothing to any editor until it's turned off and on, and the freeze and table commands find no cell to act on. The check script uses `use(false)` too, to compare against Obsidian's own table where its checks say *against the switch off*, and `breakCopy` in `language.ts` to make the copy fail; its *Fallback* section, last, checks all this (`window.__checkFallbackOnly`, with `__checkOwnOnly` and `__checkCellsOnly`). The plugin's debug hook is `debug` on the plugin, and `preview` too, for `.dev/measure`'s timing scripts, which compare against builds from before the relaunch. Obsidian's right-click Row, Column and Sort items and its table commands are rebuilt on it (*Editing rows and columns*, in `own-table-edits.md`), and so are its drag handles and + buttons (*Drag handles and + buttons*, in `own-table-edits.md`).

**What it relies on in Obsidian.** Read from 1.15.1 and checked by the *Own* section of `scripts/obsidian-check.js`.

1. Obsidian finds a Live Preview table only by the line class `HyperMD-table-row` in the syntax tree (its Live Preview builder; two other checks read `HyperMD-table` and `HyperMD-table-2`).
2. A note's editor gets its Markdown language in `buildLocalExtensions`: a `StreamLanguage` of the CodeMirror 5 mode `hypermd` (`parseFrontmatter ? Ake : Pke`), and nothing compares it by identity. So a copy made with `StreamLanguage.define` from its `streamParser` (internal to CodeMirror), whose token function gives a table row's first token only `line-selectable-tables-row` and its other tokens nothing (`hide-rows.ts`), hides every table from Obsidian: it builds no table object, and its parser no longer reads every table to its end, since rows lose `line-parse-next`. HyperMD keeps the table it's in on its state as `hmdTable`. This is the private change.
3. Obsidian's parser gives every line with a class one node over the line, and its own `@codemirror/language` exports the prop holding the classes as `lineClassNodeProp`; CodeMirror's doesn't, so it's read by name (`tree-rows.ts`).
4. The copy goes in as the editor is made: a `language.computeN` at `Prec.highest` gives it in Live Preview and nothing in Source mode, from a field that holds the copy for the editor (`language.ts`). Obsidian creates a note's state with `editorEditorField` and `editorInfoField` set, and the plugin's extensions in it, so the field can tell a note's editor (its info is a `MarkdownView`, and it isn't inside a `.cm-table-widget`) and give it the copy of the language the last note's editor had. The first note after Obsidian starts, or after the switch goes on, gets it a moment later, from a view plugin, after one first parse on Obsidian's language. Obsidian's own cell editors and editors outside a note (a canvas card) keep Obsidian's language and its tables. Before using a copy, the plugin parses a small table with it and checks the rows it marks; if the copy can't be made, after an Obsidian update say, it leaves tables to Obsidian and says so once.
5. Tables start where the parser marks a header row; each one's end is read from the text, by the parser's own rule (`rowRule` in `find.ts`: a header starting with a pipe goes on while lines start with one, any other while a line has a pipe after a first character that isn't one). The parser reads only so far past the screen, and when it's 100,000 characters behind the screen it starts again near it, leaving the stretch between with nothing on it: a table there keeps its place while its text still opens a table. After a change, `updateTables` reads only from the line above the first change to where the parser has read, and skips over tables it still marks.
6. `MarkdownRenderer.render` draws a table's rows as Reading view does, and the editor's own link handling (`registerDomEvents` on its content, with `Dv`) follows a link in a rendered cell and shows its preview on hover, as in Obsidian's table. It doesn't mark a link to a missing note, so the renderer does (`getFirstLinkpathDest`). Its table post-processor sets each cell's `dir` from its first strong character before `render` returns, reading it with a node iterator rooted at the cell (`G6`); Obsidian's own table also puts the first cell's on its box, so a table whose first cell reads right to left runs from the right. The renderer puts the first header cell's on each block and on the box around them, and each cell's on the cell's own box (`.table-cell-wrapper`): cells that draw their own borders do it by direction, and a cell reading the other way would leave the table's end bare. A document keeps every node iterator until a garbage collection and checks each one whenever a node in it moves, and an iterator follows its root into another document. So `renderBatch` renders each batch in a document of its own and moves only the cells' contents into cells it makes in the page, with the rendered cells' attributes. Rendered in the page, a fast scroll piled up thousands of iterators there, and every change in the page, Obsidian's too, got slower until the next collection.
7. A table of up to 100 rows is one block widget carrying Obsidian's classes for its table (`cm-embed-block cm-table-widget markdown-rendered`), so Obsidian's look and a theme's land on it; a longer one is a block per 100 rows, each such a widget (item 9). A block's `coordsAt` says where each row is, or CodeMirror scrolls to the block's end for a line in it. Columns get fixed widths worked out from the text with the theme's fonts and sizes (`estimate.ts`, read by `metrics.ts` from a hidden table), so they hold as rows come and go. Rows are drawn to 1,500 px past the pane, measured, and the row at the pane's top kept still while rows above take their real heights. Spacer rows stand in for the rest, hidden from screen readers, and a hidden row keeps the drawn ones odd or even; each drawn row carries `aria-rowindex` and the table `aria-rowcount`, so a screen reader hears where a row sits in the whole table. Where the theme collapses borders, the box takes `selectable-tables-own-borders`, as a frozen table does, and its cells draw their own: collapsed borders belong to the whole table, so each row added repainted all of it on screen, and hard flicks blanked the pane about twice as often. The first column gets half of each of its borders back, so its text has the room it has in Obsidian's table.
8. A press on a cell opens it (*Editing a cell*, in `own-table-cell-editing.md`), and a press beside the cells, or on the box around a table's blocks, selects the table whole, with Obsidian's tint and the frame `styles.css` draws for a selected table. Typing over it does nothing (`stopsEdit`, as for the navigation layer); Delete, cut and paste act on it.
9. CodeMirror puts a box around a run of lines, a block wrapper (`@codemirror/view` 6.39; Obsidian 1.15.1 bundles 6.43 or later). Each table of more than 100 rows gets one around its blocks (`boxes.ts`), with Obsidian's classes for a table's box, so Obsidian's and a theme's sizes for that box (its reach into the margins, its padding beside the table, a theme's width) land on it once. The blocks inside drop them, `!important` for their margins, since Obsidian and themes set a table box's margins that way; and the box drops its padding above and below, which CodeMirror can't see, so the first block keeps the padding above and the last the padding below. Themes style a table's first and last rows, so each block has hidden first and last rows that only count for those rules, and a hidden row keeps every drawn row odd or even as in the whole table. On a phone or tablet the box scrolls the blocks sideways together; on a computer it clips them (item 12). CodeMirror makes the box anew whenever the first block it draws changes, and the new box starts at the table's left edge, so a mutation observer on the content puts it back where the table was, before the frame is drawn; only a box just put in the page, so the box already there keeps a swipe's place. `@codemirror/view` stays outside the bundle, so block wrappers are Obsidian's at run time; without them the plugin leaves tables to Obsidian and says so once.
10. CodeMirror keeps the note still on its scroll anchor: the line block at the scroll offset plus 8 px, from its own heights, at the start of a measure (`scrollAnchorAt`), and moves the note for any change of height above that block. So the plugin keeps the row at the pane's top still only for rows above it in that same block, and a block coming into view starts at its full estimated height, its rows not drawn yet standing in as spacers; otherwise both would move the note for the same rows. CodeMirror keeps a block's height until it draws it again, and takes an estimated height only from a new decoration, so tables shaped since they were decorated (before they had sizes, or after the pane or the theme changed) are decorated again.
11. With blocks, the screen can start inside a table, so after the parser's 100,000-character jump (item 5) it can start again on one of a table's rows and read the rest as text, its header in the stretch it skipped. An edit above the table with the note scrolled to its end does this, for about 12 frames before the parser reads the header again. A table the plugin already knows is kept while its header is in a stretch the parser skipped and its text still opens a table (`updateTables`), so it's never drawn as lines of text.
12. **Sideways, on a computer (STA-79).** A box that scrolls a table sideways stops its rows sticking to the note (item 13 of the list in `obsidian-table.md`), so on a computer no box does: the table's box, its one block or the box around its blocks, clips it (`overflow: clip`, which makes no scroll container), and each block's `.table-wrapper` moves by a transform that follows a scrollbar of the plugin's own (`bar.ts`), a scroll-driven animation on the compositor, so the blocks move as one with no script as they move. The bar is a scroller in the note's `.cm-scroller`, as wide as the table's box, whose content is that much wider than the table can move: its scroll is the table's place sideways, kept while the table is wide, so it survives the table leaving the pane and CodeMirror rebuilding its box. Its `scroll-timeline` is named per table and hoisted by `timeline-scope` on the scroller, so every block in it can follow it. It sits in the scroller, not beside it, so scrolling up and down with the pointer over it scrolls the note, and it has no styling of the plugin's, so on a Mac it's the system's own bar and follows Show scroll bars, and elsewhere Obsidian's `styled-scrollbars` styles it. Its place up and down is an animation on the note's own scroll: it sits under the table's last row, in the box's bottom padding, and between two scroll offsets worked out from where the header and the last row sit in the note's content, it rides the pane's bottom, clear of the status bar (`.status-bar`, read where it floats over the pane), so it never trails a scroll; the sums are `barPlace` in `sideways.ts`. A table no wider than its box gets no bar and no transform. The scroll range is rounded to whole pixels, as Obsidian's box rounds its own, which also keeps the table's lines sharp. A swipe over the table sends no scroll the browser can use, so a wheel listener on the content, not passive, passes the sideways part of a mostly sideways swipe to the bar and stops the note scrolling for it, and leaves a swipe that starts up or down alone (`Swipes`): as in Obsidian's box, where the browser keeps a swipe to where it began. Obsidian already listens for the wheel that way on the note's view, for Ctrl-zoom, so a swipe's first event waited on the page before. A swipe starts anew after a pause of 80 ms, or when the browser starts one, which it marks by letting its first event be cancelled. Ctrl with the wheel, and a pinch, are Obsidian's. Phones and tablets keep the box, scrolled by a finger, which sends no wheel events, and so do browsers without scroll-driven animations: `usesBars` reads `is-mobile` on the body and `CSS.supports`, and the editor carries `selectable-tables-bars` when it uses bars. `showSideways` on a model brings part of a table into view sideways, in the bar or the box, for the table keys, the open cell and frozen columns to use. A block that comes into the page carries the bar's timeline from its first frame, so it's drawn where the table is.
13. **Its stylesheet comes after its start-up.** Obsidian adds a plugin's `styles.css` only after its `onload` (`loadCSS`), on a reload as at start-up. So the plugin draws no table until its stylesheet is in: `styles.css` sets `--selectable-tables-styled` on the body, and `whenStyled` in `tables.ts` waits for it. Drawn without it, the hidden probe beside the note took room, the note narrowed and every table was laid out again, and Obsidian's own editor code, which measures in each update, kept that chain going without a break, so the stylesheet never got its turn: a reload with a wide table in view froze the window until its renderer ran out of memory (STA-80).
14. **A right-click's menu.** The plugin's table has no menu of Obsidian's, so Obsidian's editor would show its own, from its `onContextMenu`. That handler waits for Electron's context-menu event, then gives up if the event's default has been prevented, so a `Menu.forEvent` from a listener on the note's content (`tableMenus`) is the only menu shown, as over Obsidian's table. *Own 70* checks that one menu shows. On a phone or tablet, Obsidian turns a long press, 800 ms, into a `contextmenu` event on what's under the finger, from a `touchstart` listener on the window, so the same listener shows a cell's menu there.
15. **Its handles' and buttons' look.** Obsidian's `app.css` styles `.table-row-drag-handle`, `.table-col-drag-handle`, `.table-row-btn` and `.table-col-btn` inside a `.cm-table-widget`, its cells `position: relative`, and its `.table-wrapper` too: hidden, and shown on hover on a computer; on `is-mobile`, the handles only in cells marked `mod-active-row-handle` and `mod-active-col-handle`, and the buttons only in a widget marked `has-focus`; while a handle is held, `is-dragging` on the widget hides the others. Its blue line is `.table-drag-target` with `mod-row` or `mod-col`, positioned in the widget. So the plugin's copies of them take Obsidian's look and a theme's.
16. **A range's look.** Obsidian's `app.css` draws a range of cells from classes on its cells, inside a `.cm-table-widget`: `is-selected` tints a cell with `--table-selection` by an `::after` that reaches over its borders, and `start`, `end`, `top` and `bottom` give that `::after` the frame's border, `--table-selection-border-width` in `--table-selection-border-color`, on the range's edges, rounded at its corners (read from 1.15.1's `selectCells`). So the plugin's range takes Obsidian's look and a theme's. *Own 111* checks the frame and the tint from computed styles and the window's picture.
17. **Its table data on the clipboard.** Obsidian's range copies `obsidian/table`, JSON of `{rows, alignment}`: each cell's Markdown, row by row, and each column's alignment (1.15.1's `copySelection`), and its open cell's editor reads it first on a paste, at Prec.high (`pasteSelection`), leaving anything else to the editor's own paste. So cells move between Obsidian's table and the plugin's both ways. *Own 139* checks it.
18. **Formatting.** Every formatting command and the Formatting submenu call one of four methods of the note's `Editor`: `toggleMarkdownFormatting(kind)`, `toggleHighlight(color?)`, `toggleComment()` and `clearMarkdownFormatting()` (1.15.1). Each acts on `getFormattingRanges()`, the cells of Obsidian's range (`getTableSelection()`) or else the selection, reads what's already formatted from the syntax tree of the `Editor`'s `cm`, which its `init` fixes to the note's view, and dispatches its change there. On a range the first cell decides whether it goes on or comes off, and an empty cell is skipped. The base Markdown editor makes its own `Editor`, `editor`, over its own view. *Own 146* checks these.
19. **The link commands.** Follow link under cursor (`editor:follow-link`, Option+Enter) and the three that open in a new tab, to the right or in a new window (`editor:open-link-in-new-leaf`, `-split`, `-window`) look for a link at the note's caret with the note's `Editor`'s `getClickableTokenAt`, which reads token classes from the note's tree. The plugin's rows are bare (item 2), so they find none, and a hotkey then dispatches `new CustomEvent('open-link', {bubbles, cancelable, detail: {paneType}})` on the active element, `paneType` being `false`, `'tab'`, `'split'` or `'window'` (1.15.1). The palette's check returns nothing there, so the palette doesn't list them. Obsidian's Bases table answers the same event for its selected cell. *Own 187* checks the event.

**Matching a theme (STA-88).** What it took to match Obsidian's table within a pixel under the 21 themes:

- The hidden table `metrics.ts` reads sits in a hidden stand-in for the note's content, beside it with its classes (`selectable-tables-probe-content`), so a theme's rules for a table in the content reach it, Typewriter's padding say, and it takes the width a table has there, as under Minimal's line width. Put in the content itself, it would be an edit to CodeMirror.
- A theme's font loads once text first uses it, after the plugin may have measured with the font standing in for it, and Obsidian sends nothing then: `tables.ts` lays tables out again on `document.fonts`' `loadingdone`, and the text widths kept are forgotten.
- A change of look makes every editor's sizes out of date (`lookChanged`), with the switch on or off: forgotten only in editors the plugin was drawing in, a theme changed with the switch off left tables laid out with the theme before once it was back on (Brian's hand check, 11/20; `Own 17`).
- Where a theme keeps every space (`break-spaces`, as the default theme does), a line breaks only after its spaces, so a word not last on its line takes its space with it, which sets a column's narrowest width. A word runs on across styled spans until a space.
- Widths are kept to a 64th of a pixel, as the browser lays a table out: whole pixels moved the lines after each column. Between their narrowest and widest, Chromium shares the room by how much more each column wants, and WebKit, on an iPhone or iPad, column by column by how wide each wants, taking any excess back from the last (`shareAsWebKit`).
- Joined borders lie half in each cell beside them; a theme that keeps them apart has each cell hold its own whole, and the table's own borders and spacing count too. A theme that stretches tables, Typewriter or Baseline, has the room left shared out by how wide each column wants.
- A theme's border on the table itself is drawn only at the table's ends, not at its seams. The blocks in a box are `fit-content`, not `max-content`, since a theme that makes every table 100% wide (Border, Tokyo Night) gave a table of percentage width a million pixels of max-content.
- A picture or a player has no size in its text. Once it has one (a picture's `load`, a video's `loadedmetadata`, a player at once), `measureContent` measures a copy of its cell alone in a hidden table, squeezed and spread, as the browser does a cell, and the columns are fitted again, without the note moving. The size is kept by the cell's text, and measured again after a change of look.
- An empty cell holds a line break, as Obsidian's does, so a row of empty cells is a line tall.

The misses left, each in one theme, are listed in STA-88's PR. A theme's own table settings (row numbers, AnuPpuccin's table styling) aren't matched yet: STA-94.

**Timing** is `.dev/measure`'s `measure-real-table.js`, and for blocks `measure-blocks-real.js`, run with each build to compare; their README says how. Blank bands on hard flicks are `measure-flicks.js`'s: it counts them in the frames the screen gets, since `capturePage` waits for the page and never sees the screen run past the drawn rows. A real hard flick runs far past 6,000 px/s, so time 12,000 to 40,000, interleaving what you compare, since runs vary widely. And time it with an accessibility client running, as anyone using a screen reader or a tool that labels what can be clicked has it: Obsidian then updates its accessibility tree for the rows each draw adds, 18 to 37 ms a time, which is most of what still lets the screen outrun the rows. `@codemirror/language` is a dev dependency for its types only, pinned at 6.13.1 with the same `@codemirror/state` as `obsidian`; Obsidian 1.15.1 bundles at least 6.12.3 (its bracket matcher and its stream parser's chunk size match that version), and the renderer uses only what 6.0 already had.
